## Critical Issues

1. **Log WebSocket reconnects on every container status update** — `components/ContainerLogs.vue:83-88,191` [Gemini 3.1 Pro] (critical, regression)

```typescript
const logURL = computed(() => {
  if (!genericLogURL.value || !container.value?.metadata?.name) {
    return undefined;
  }
  return new URL(container.value.metadata.name, genericLogURL.value);
});
```

The `logURL` computed (line 87) returns `new URL()`, which creates a fresh object on every evaluation. The `container` computed (line 73) depends on the store getter `containerById`, which re-evaluates whenever the informer pushes any status update. Because Vue's `watch` at line 191 compares array elements with `Object.is()`, the new URL reference triggers the watcher even when the URL string has not changed. Each trigger aborts the active WebSocket (line 197-199), resets the terminal (line 201-204), and opens a new connection (line 219). The result: log output flickers and reconnects whenever any container's status changes in the background.

Fix: Return a string primitive so Vue compares by value.

```diff
-  return new URL(container.value.metadata.name, genericLogURL.value);
+  return new URL(container.value.metadata.name, genericLogURL.value).toString();
```

## Important Issues

1. **Namespace refresh dispatches wrong payload shape** — `store/container-engine.ts:105-108` [Codex GPT 5.4] (important, regression)

```typescript
for (const key of Object.keys(state._watchers)) {
  dispatch(`watch${ key.replace(/^\w/, c => c.toUpperCase()) }`,
    { options: state._watchers[key as resourceKeys].options });
}
```

The `setCurrentNamespace` action at line 107 wraps the stored options in `{ options: ... }`, but `resourceWatchActions` at `rddConnection.ts:305` consumes the payload directly as `options?: ResourceWatchActionsOptions`. The action receives `{ options: { callback, namespace } }` instead of `{ callback, namespace }`, so `options?.namespace` and `options?.callback` resolve to `undefined` at lines 321 and 333. The corrupted payload is then persisted back into `_watchers` at line 348, breaking all subsequent reconnects.

This bug is dormant because `supportsNamespaces()` returns `false` (line 67), so `setCurrentNamespace` never reaches the dispatch loop. It will break the moment namespace support is enabled.

Fix: Pass the stored options directly.

```diff
  dispatch(`watch${ key.replace(/^\w/, c => c.toUpperCase()) }`,
-    { options: state._watchers[key as resourceKeys].options });
+    state._watchers[key as resourceKeys].options);
```

```typescript

  // ...
```

A failing WebSocket emits both `error` and `close` events. Each calls `handleStreamError()` at lines 291 and 303, which schedules a `setTimeout` at line 323 without guarding against a pending timer.      const delay = Math.pow(2, reconnectAttempts) * 1_000;
```diff
-    setTimeout(() => {
+    clearTimeout(reconnectTimer);
+    reconnectTimer = setTimeout(() => {
       reconnectAttempts++;
       reconnectTrigger.value++;
     }, delay);
   }
 }
```

1. **Log reconnects are scheduled twice for one socket failure** — [ContainerLogs.vue](/Users/jan/git/rancher-desktop-app/pkg/rancher-desktop/components/ContainerLogs.vue#L279) (suggestion, regression)

```ts
socket.addEventListener('error', () => {
  handleStreamError();
});
socket.addEventListener('close', (event) => {
  if (!event.wasClean) {
    handleStreamError();
  }
});
```

The new reconnect logic calls `handleStreamError()` from both the `error` handler at [ContainerLogs.vue](/Users/jan/git/rancher-desktop-app/pkg/rancher-desktop/components/ContainerLogs.vue#L279) and the `close` handler at [ContainerLogs.vue](/Users/jan/git/rancher-desktop-app/pkg/rancher-desktop/components/ContainerLogs.vue#L293), and `handleStreamError()` itself just queues a fresh `setTimeout()` at [ContainerLogs.vue](/Users/jan/git/rancher-desktop-app/pkg/rancher-desktop/components/ContainerLogs.vue#L321) without deduping or clearing older timers. ### Executive Summary

This PR successfully migrates the containers page to the new RDD API, replacing the previous Docker CLI-based implementation. The author has addressed the feedback from Round 1, fixing the `spec.desiredState` payload, sorting keys, Vuex getter mapping, and stale props. However, the migration of the WebSocket connection logic in `ContainerLogs.vue` introduces a critical regression where the log terminal will continuously disconnect and reset whenever the container's background status updates.

### Findings

#### Critical Issues

1. **Constant log reconnections due to reactive object identity** — `pkg/rancher-desktop/components/ContainerLogs.vue:85-90` (critical, regression)

```typescript
const logURL = computed(() => {
  if (!genericLogURL.value || !container.value?.metadata?.name) {
    return undefined;
  }
  return new URL(container.value.metadata.name, genericLogURL.value);
});
```

Because `logURL` depends on `container.value` (which is sourced from the store via `containerById`), it re-evaluates whenever the background container status updates (e.g., from an informer update for CPU stats or conditions). This computed property creates and returns a `new URL()` instance every time it runs. Vue's `watch([logURL, ...])` compares arrays of objects using strict reference equality (`===`). Since the new `URL` instance is a different object reference, the watcher triggers, repeatedly aborting the active WebSocket connection and resetting the terminal.

Fix: Return a primitive string instead of an object to ensure the watcher only triggers when the actual URL value changes.

```diff
-  return new URL(container.value.metadata.name, genericLogURL.value);
+  return new URL(container.value.metadata.name, genericLogURL.value).toString();
```

#### Important Issues

None.

#### Suggestions

1. **Duplicate watchers for cluster-wide ConfigMaps** — `pkg/rancher-desktop/store/rdd.ts:18-24` (suggestion, enhancement)

```typescript
  defineResource({
    name:       'systemConfigMaps',
    type:       'ConfigMap',
    path:       '/api/v1/configmaps',
    makeClient: config => config.makeApiClient(RDDClient.CoreV1Api),
    list:       client => client.listNamespacedConfigMap({ namespace: 'rdd-system' }),
  }),
```

The new `systemConfigMaps` resource uses the same cluster-wide `path` (`/api/v1/configmaps`) as the existing `configMaps` resource. Since `rddConnection` watches the endpoint defined by `path`, this will open a second concurrent WebSocket connection to the identical endpoint, duplicating cluster-wide ConfigMap traffic. Consider whether these resources could be consolidated or if the path should be scoped specifically to `rdd-system` (`/api/v1/namespaces/rdd-system/configmaps`) to reduce unnecessary traffic.
