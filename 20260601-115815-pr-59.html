I2. New supply-chain checksum parsers ship without unit tests Claude¶
scripts/lib/dependencies.ts
/**
 * Parses a raw string as a {@link Sha256Checksum}.  Throws unless the value
 * has the form `sha256:<64 hex chars>`.  Uppercase hex parses but normalizes
 * to lowercase so consumers can compare with `===`.
 */
export function parseSha256Checksum(value: unknown): Sha256Checksum {
  if (typeof value !== 'string' || !/^sha256:[0-9a-f]{64}$/i.test(value)) {
    throw new Error(`Invalid sha256 checksum ${ JSON.stringify(value) }; expected "sha256:<64 hex chars>"`);
  }

  return value.toLowerCase() as Sha256Checksum;

These three new functions guard the install-time integrity contract, and their parsing is intricate: GNU (<hex> <file>) versus BSD (ALG (<file>) = <hex>) line formats, a hex-width anchor that rejects a wrong-algorithm sidecar, and a basename-alias dedup on collision. The comments document edge cases that no test exercises — scripts/lib/__tests__/ holds only build-utils.spec.ts. A regression in any branch would silently weaken digest verification, and the functions are pure (string in, map out), so they are cheap to test.

Fix: add scripts/lib/__tests__/dependencies.spec.ts covering GNU/BSD lines, wrong-algorithm width rejection, basename-collision dedup, and parseSha256Checksum accept/reject/normalize cases.

Design Observations ¶

Concerns ¶

  • Steve has no internal lifecycle owner (in-scope) Codex Gemini — Start and stop hang entirely off the renderer's KubernetesReady status event (background.ts:251-260) plus before-quit. I1 (no restart on exit) and S1 (no kill on readiness failure, no awaited teardown) all stem from this single external driver. A Steve manager that owns its own restart-on-crash, kill-on-failure, and awaited teardown would close the whole class at the source instead of patching each path.
  • download() codesign cache-hit never repairs destPath (future) Claude — On a cache hit, download() hashes ${destPath}.unsigned and returns without confirming destPath exists or re-running codesign. The rework correctly hashes pre-signature bytes (fixing the "digest after mutation" hazard), but a future caller that sets codesign: true would ship a missing or stale signed binary if destPath is deleted while .unsigned survives. No current caller sets codesign, so it cannot fire today; the latent bug lands with the first consumer.

Strengths ¶

  • Digest pinning Claude Codex — dependencies.yaml records an immutable commit alongside mobyOpenAPISpec's version, and downloadAndHash hashes as-downloaded bytes before any mutation; archives cache next to destPath and are excluded from packaging.
  • Steve readiness probe Gemini Claude — steve.ts waits on /v1/namespaces (404 until the schema controllers register) rather than treating an open port as ready.
  • Host-switch handshake retry Claude — the acceptWithTimeout path closes the listener to unblock Accept, drains the channel, and closes the racing connection, handling the goroutine leak cleanly.
  • Reduced main-process surface Codex — removing the dashboard proxy and its certificate allowlist deletes a class of special cases.

Testing Assessment ¶

Ranked by risk:

  1. Checksum parsers are untested — see I2; the highest-value gap, since the logic guards supply-chain integrity and is trivially testable.
  2. Steve lifecycle (steve.ts, 242 lines) has no unit tests — start/stop/restart, stdout port parsing, the stale-process guard (childProcess !== this.process), and the dual timeouts are unexercised. It spawns a real process and uses IPC, so extract the port-parse/readiness logic for isolated tests or add an integration smoke test.
  3. The unexpected-exit-after-ready path (I1) and the readiness-failure path (S1) have no coverage.
  4. Dashboard e2e is test.describe.fixme (e2e/dashboard.e2e.spec.ts), matching the RDD-migration norm where many e2e suites are disabled, so the headline feature is validated manually until those re-enable — not a regression.

Review Process Notes ¶

Skill improvements ¶

  • Derive the prompt's Changed Files list from the same merge-base diff that produces the reviewed patch, not from the hosting platform's PR file metadata. When the list comes from the platform's API while the patch is computed locally against the merge-base, the two can diverge — the platform may use a different merge-base or paginate its file set — and any agent that builds its coverage summary from the Changed Files list then silently skips files that appear only in the patch. Generate the list with git diff <merge-base>..<head> --name-status so it always matches the diff under review.
