## Executive Summary

This PR replaces the hard-coded `rancher-desktop` Kubernetes namespace used by the `container-engine` Vuex module with the `App` custom resource's `spec.namespace`. A new plugin in `container-engine.ts` watches the `rdd/kubernetesNamespace` getter and re-runs `setupResourceWatch` when the value changes. A companion commit (`441c664fa`) corrects every Vuex `Plugin<T>` annotation from per-module state to `RootState`, since plugins receive the root store.

The architectural direction is right — the renderer-side store now follows the daemon's API model rather than a frontend constant — and the `flattenedGetters` mapped type added to `ts-helpers.ts` is a tidy enhancement that gives `rootGetters` lookups compile-time safety. The rough edges concentrate around the plugin's startup conditions: the watcher only initializes on a namespace *transition*, so if `App.spec.namespace` is implicit (the CRD documents `"default"` as its default), `container-engine` never starts; the symmetric `rdd` module was not given the same re-watch wiring; and `setupResourceWatch` is now reachable from a new trigger in addition to the pre-existing reconnect path, exposing a concurrency gap. None are blocking, but I1 and I2 are worth a fix before merge.

I1. **Container-engine watches never start when `App.spec.namespace` is unset** — `pkg/rancher-desktop/store/container-engine.ts:253-275`, `pkg/rancher-desktop/store/rdd.ts:54-57` [Codex GPT 5.4, Gemini 3.1 Pro]

```ts
    (newNamespace: string | undefined) => {

```

The plugin's only path to dispatching `setupResourceWatch` is a transition in `rdd/kubernetesNamespace`. The getter at `rdd.ts:54-57` returns `app?.spec?.namespace` directly, and the `App` model lists the field as optional:

```ts

* manages its owned namespaced resources (e.g., rancher-desktop). Defaults to
```

I2. **`rdd` module's namespaced watchers stay locked to the initial fallback** — `pkg/rancher-desktop/store/rdd.ts:139-151`, `pkg/rancher-desktop/store/rddConnection.ts:385,389` [Claude Opus 4.7, Gemini 3.1 Pro]

`rddConnection.ts:385/389` resolves the namespace via `rootGetters['rdd/kubernetesNamespace'] ?? 'default'`, evaluated once per `setupResourceWatch` call. `rdd/configMaps` has no consumer today (only `systemConfigMaps`, hard-coded to `rdd-system`, is consumed in `composables/passthrough.ts:31`), so the bug is latent. But the design now has two modules with namespaced resources following different rules for the same "namespace from app" requirement — the next consumer of `rdd/configMaps` will hit a silent wrong-namespace bug.

Fix options, in order of preference:
1. Drop the unused `configMaps` resource from `rdd.ts` (YAGNI). Re-add it with proper plumbing when a caller appears.
2. Extract the `let currentNamespace; store.watch(...)` pattern from `container-engine.ts` into a shared helper (e.g., `watchNamespacedResources(module)` in `rddConnection.ts`) and adopt it in both modules.
3. Add an `autoRewatchOn(getterPath)` option to `resourceWatchActions()` itself, so the mechanism lives next to the action that needs it.

I3. **`setupResourceWatch` is not concurrency-safe** — `pkg/rancher-desktop/store/rddConnection.ts:357-455`, `pkg/rancher-desktop/store/container-engine.ts:259-274` [Claude Opus 4.7, Gemini 3.1 Pro]

```ts
async setupResourceWatch(actionContext: ActionContext<State>, options?: ...) {
  ...
  while (!rddState.config.currentContext) {
    try {
      await dispatch('rdd-connection/fetchConfig', {}, { root: true });
    ...
  try {
    state._watchersInitialized.reset();
    for (const r of resources) {
      const resourceOptions = Object.assign({}, state._watchers[r.name]?.options, options ?? {});
      state._watchers[r.name]?.watcher?.close();
      const client = r.makeClient(rddState.config);
      const watcher = new Watcher( ... );
      ...
      commit('SET__WATCHERS', { ...state._watchers, [r.name]: { watcher, ... } });
      ...
      await dispatch('rdd-connection/registerDisconnectCallback', ...)
```

`setupResourceWatch` now has three triggers: the namespace watch (container-engine.ts:266, new in this PR), `setCurrentNamespace` (container-engine.ts:103), and the reconnect path (rddConnection.ts:412-422). It awaits inside the per-resource loop (the `registerDisconnectCallback` dispatch at 441-448), so two invocations can interleave their close → create → commit → register sequence and leave `state._watchers` referencing the loser's watcher. The visible symptoms: a ghost watcher with a still-armed 429 retry `setTimeout` (rddConnection.ts:583-592) running against the old namespace, or `_watchersInitialized` resolved against a half-replaced watcher set.

The reconnect path already exposed this race, but the namespace-change trigger makes it reachable on every normal startup, not just on backend reconnects.

Fix: serialize invocations with a per-module in-flight promise, mirroring `fetchConfigPromise` at `rddConnection.ts:56-86`. Collapse a back-to-back call into the trailing one. As a cheap defense-in-depth, add a `#stopped` flag to `Watcher` and short-circuit the 429 retry `setTimeout` if it fires after `close()`.

(important, regression)

S7. **`Watcher` identity-only filter on `errorManuallyStopped` is fragile** — `pkg/rancher-desktop/store/rddConnection.ts:578-583` [Gemini 3.1 Pro]

```ts
this.#watcher.on('error', (err) => {
  if (Object.is(err, errorManuallyStopped)) {
    // The watcher errored out because we called stop(); do not propagate
    // this as an actual error.
    return;
  }
```

The pre-existing pattern relies on `controller.abort(reason)` propagating `signal.reason` verbatim through `fetch` and `ReadableStreamDefaultReader.read()`. Modern Node and browsers do this, so `errorManuallyStopped` survives the round trip and the `Object.is` check matches. This is correct today, but the round trip touches three layers (AbortController → fetch → reader), each of which could be replaced with one that wraps in a `DOMException('AbortError')`, and the symptom would be silent error propagation through `doneFn` plus a reconnect loop racing the new watcher. The PR exercises this path on every namespace change rather than only on backend reconnects, raising the cost of any future regression.

Cheap defense-in-depth: track an explicit `#stopped` flag on the `Watcher` and check it before propagating any error from the underlying `ListWatch`.

```diff
   #watcher:     RDDClient.ListWatch<T>;
+  #stopped = false;
...
     this.#watcher.on('error', (err) => {
-      if (Object.is(err, errorManuallyStopped)) {
+      if (this.#stopped || Object.is(err, errorManuallyStopped)) {
         return;
       }
...
   close() {
+    this.#stopped = true;

```

This also folds in the I3 defense-in-depth note about the 429 retry `setTimeout` — gate `start()` on `#stopped` too. (suggestion, enhancement)

## Design Observations

### Strengths

- *(in-scope)* Moving the source of truth from a renderer-local `rdd-connection.namespace` field to the App resource matches the daemon's API model rather than a hard-coded frontend constant. [Codex GPT 5.4, Claude Opus 4.7]
- *(in-scope)* Strongly typing `rootGetters` via the new `flattenedGetters` mapped type gives compile-time safety to cross-module lookups like `rootGetters['rdd/kubernetesNamespace']`, and lifts `UnionToIntersection` into `utils/typeUtils.ts` where the second consumer (`ts-helpers.ts`) can share it. [Gemini 3.1 Pro, Claude Opus 4.7]
- *(in-scope)* Reusing `resourceWatchActions()` for the namespace-driven reconfiguration keeps the watch lifecycle logic in one place rather than scattering one-off watcher code across each page. [Codex GPT 5.4]
- *(in-scope)* The `Plugin<RootState>` typing fix in commit `441c664fa` lands uniformly across all four modules with `plugins`. [Claude Opus 4.7]

### Concerns

- *(future)* The "plugin that watches a getter to re-setup resources" pattern will be duplicated the moment a second consumer of `rdd/configMaps` (or any other namespaced rdd resource) appears (see I2). An `autoRewatchOn(getterPath)` option on `resourceWatchActions()` would centralize the mechanism. Not urgent — raise it when the second consumer arrives. [Claude Opus 4.7]
- *(future)* The effective Kubernetes namespace now lives in three states: "App missing", "App present with explicit namespace", "App present with implicit default". Centralizing the normalization in one helper would prevent future namespaced resources from making different fallback choices. [Codex GPT 5.4]

## Review Process Notes

### Skill improvements

- **Treat "watcher shutdown" abort plumbing as runtime-version-dependent, not an automatic critical.** When a finding alleges a deliberate-shutdown error leaks through identity comparison (e.g., `Object.is(err, sentinel)` failing because the runtime wraps the abort reason), trace the abort chain end-to-end before promoting to critical. In modern Node and browsers, `AbortController.abort(reason)` propagates `signal.reason` verbatim through `fetch` and `ReadableStreamDefaultReader.read()`, so the sentinel survives. Reserve "critical" for cases where the runtime contract demonstrably wraps the reason; otherwise downgrade to a defense-in-depth suggestion.

- **For Vuex/Vue reactive `store.watch` callbacks, treat "guard against same value" as redundant for primitive sources.** Vue's reactive `watch` fires only when the source value changes. Code that caches the previous value and compares inside the callback (`if (newValue === cached) return;`) is dead defensive code on a primitive getter. Flag the redundancy as a suggestion, but verify the source is primitive — for object getters, identity-stable references can cause re-fires that the guard would catch.

### Repo context updates

- **[repo] `rdd/kubernetesNamespace` getter is the source of truth for the namespace.** When reviewing code that reads or writes Kubernetes namespaces in the renderer, check whether it goes through `rdd/kubernetesNamespace` (rdd.ts) or hard-codes a string. The pre-PR pattern used `rdd-connection.namespace` and a hard-coded `'rancher-desktop'`; both are gone after PR #47. Stale mappings of either form (e.g., `mapTypedState('rdd-connection', { x: 'namespace' })`) are dead code that should be removed or repointed at the new getter.

- **[repo] `setupResourceWatch` is now reachable from three triggers, not one.** When reviewing code that calls or modifies `setupResourceWatch` in `pkg/rancher-desktop/store/rddConnection.ts`, account for: the namespace-change watch (container-engine plugin), `setCurrentNamespace`, and the reconnect path inside `setupResourceWatch` itself. The function does `await` inside its per-resource loop and is not serialized, so two concurrent invocations can interleave. Flag any code that adds a fourth trigger without addressing serialization.

- **[repo] App `spec.namespace` is documented as defaulting to `"default"` server-side, but the TypeScript surface keeps the field optional.** When reviewing renderer code that reads `app.spec.namespace`, treat the value as `string | undefined` regardless of the CRD documentation — generated client code does not enforce the default. Code that depends on the field being defined needs an explicit fallback.

**Verdict:** Approve with minor suggestions

### Executive Summary

This PR replaces the hard-coded `rancher-desktop` namespace used for container-engine resource watches with a value read from the `App` custom resource's `spec.namespace`, and re-runs `setupResourceWatch` when that value changes. A companion commit fixes the Vuex `Plugin<T>` type to use `RootState` consistently. The plumbing is straightforward and correct; the rough edges are scoping nits around the re-watch trigger, a comment/name polish, and a latent inconsistency in `rdd.ts`.


```ts

  ...
  while (!rddState.config.currentContext) {
    try {
      await dispatch('rdd-connection/fetchConfig', {}, { root: true });
```

`setupResourceWatch` is now invoked every time `rdd/kubernetesNamespace` changes (container-engine.ts:266), and also by `container-engine/setCurrentNamespace` (container-engine.ts:103) and by the reconnect path (rddConnection.ts:412-422). The function is not idempotent-safe: it does `state._watchersInitialized.reset()` (line 378), then `await`s `r.path(...)` round trips inside the loop, then commits `SET__WATCHERS`. Two concurrent invocations (e.g., `undefined → ns1 → ns2` in quick succession, or a namespace change that lands while the reconnect path is looping) can interleave their close/create/commit sequence and leave `state._watchers` pointing at a watcher whose companion `disconnectCallback` was already overwritten by the other invocation. The practical symptoms: ghost watcher still running after close (because the race leaves the old watcher's 429 retry `setTimeout` live — see `Watcher` constructor at rddConnection.ts:583-592), or `_watchersInitialized` resolved against watchers from the losing call.

This race pre-existed via the reconnect path, but the PR makes it reachable from a new trigger (namespace change), which happens during the normal startup path every time.

Fix: serialize `setupResourceWatch` invocations with a per-module in-flight promise (mirroring `fetchConfigPromise` at rddConnection.ts:56), or collapse back-to-back calls into a single trailing invocation. At minimum, guard the 429 retry `setTimeout` in `Watcher` against firing after `close()` — track a `stopped` flag on `Watcher` and bail out of the retry if set. (important, regression)

**C2. Deliberate watcher shutdown leaks fetch abort errors** — `pkg/rancher-desktop/store/rddConnection.ts:578-583`

```typescript
    this.#watcher.on('error', (err) => {
      if (Object.is(err, errorManuallyStopped)) {
        // The watcher errored out because we called stop(); do not propagate
        // this as an actual error.
        return;
      }
```

By restarting watchers at runtime when the namespace changes, this PR exercises `Watcher.close()` (and the underlying `ListWatch.stop()`) during normal operation. The underlying API aborts its fetch request, passing `errorManuallyStopped` as the reason. The `rdd` store defines a `configMaps` resource whose path explicitly depends on the namespace (`(namespace) => /api/v1/namespaces/${ namespace }/configmaps`). However, its plugin was not updated to react to namespace changes. It initializes exactly once at startup when `getters['rdd/kubernetesNamespace']` is `undefined`, locking the watcher to the `'default'` namespace forever. When the app object is fetched and the namespace changes, `container-engine` successfully updates its watchers, but `rdd`'s `configMaps` continues polling the old namespace indefinitely.

**Fix**: Implement the same namespace-watching logic from `container-engine.ts` into the `rdd.ts` plugin so `configMaps` targets the correct namespace.

```typescript
export const plugins: Plugin<RootState>[] = [
  function(store) {
    let currentNamespace = store.getters['rdd/kubernetesNamespace'];
    const startWatch = () => {
      store.dispatch('rdd/setupResourceWatch', {
        callback: (error: Error) => store.commit('rdd/SET_ERROR', error),
      }).catch((error: Error) => store.commit('rdd/SET_ERROR', error));
    };

    startWatch();

    store.watch(
      (_state, getters) => getters['rdd/kubernetesNamespace'],
      (newNamespace: string | undefined) => {
        if (newNamespace === currentNamespace) return;
        currentNamespace = newNamespace;
        startWatch();
      },
    );
  },
];
```

### Design Observations

#### Strengths
- Strongly typing `rootGetters` via the new `flattenedGetters` intersection mapped type in `ts-helpers.ts` is an excellent enhancement. It correctly models Vuex's flattened namespaced getter structure and instantly brings compile-time safety to cross-module `rootGetters` lookups like `rootGetters['rdd/kubernetesNamespace']`.

#### Concerns
- **Concurrency in watcher replacement (in-scope)**: `setupResourceWatch` in `rddConnection.ts` executes asynchronously over a loop of resources, yielding control during `await dispatch('rdd-connection/registerDisconnectCallback')`. If `unwatchResources` runs concurrently due to rapid namespace switching or component teardown, it will interact with `state._watchers` out-of-order, incorrectly decrementing `refCount` for replaced watchers instead of the ones it intended to close.

### Testing Assessment

The dynamic namespace capability involves orchestration loops, component lifecycles, and failure suppression, which are notably difficult to reason about safely without tests. No tests cover this change.
1. **Initial Hydration**: Verify `setupResourceWatch` runs when the store is initialized with a pre-existing `kubernetesNamespace`.
2. **Missing Spec**: Verify `setupResourceWatch` runs (with `'default'`) if the fetched `App` object lacks a `spec.namespace`.
3. **Watcher Reconnection**: Verify `ListWatch.stop()` accurately shuts down the underlying fetch without leaking an error back to the Vuex store error bindings.
