Executive Summary ¶

This PR introduces an App resource to the RDD API, starts the app on UI display, and refactors resource watching from per-resource actions to a refcounted watchResources/unwatchResources API. The refactoring centralizes watch lifecycle in setupResourceWatch, correctly handles overlapping component lifecycles through reference counting, and cleanly separates resource definitions (plugins) from consumer lifecycle (pages). Nine important issues remain: a concurrent fetchConfig race between plugins that can trigger a reconnect storm (I1), a waitForResources timing gap where it resolves before the cache populates (I2), unrecoverable error paths in ensureAppStarted (I3, I4), uncaught unwatchResources rejections in three pages (I5), a missing merge-patch Content-Type on containerSetState (I6), a spurious reconnect on watcher teardown (I7), and key collisions in disconnect callbacks (I8).

Critical Issues ¶

None.

Important Issues ¶

I1. Concurrent fetchConfig race between plugins Gemini Codex ¶

Both rdd.ts and container-engine.ts register plugins that dispatch setupResourceWatch at store initialization. Both run concurrently and hit the fetchConfig retry loop. Because fetchConfig is not deduplicated, the second call's notifyDisconnected tears down the first plugin's newly created watchers. The aborted watchers fire doneFn, which clears config and schedules another setupResourceWatch after 1 second, creating a reconnect loop.

pkg/rancher-desktop/store/rddConnection.ts
  async fetchConfig({ commit, dispatch }) {
    try {
      const config = await ipcRenderer.invoke('rdd/kube-config');
      const kubeConfig = new RDDClient.KubeConfig();

      kubeConfig.loadFromString(config);
      commit('SET_CONFIG', kubeConfig);
      await dispatch('notifyDisconnected');
      commit('SET_DISCONNECT_CALLBACKS', {});
      commit('SET_ERROR', undefined);

      return kubeConfig;
    } catch (ex) {
      commit('SET_ERROR', ex);
      throw ex;
    }
  },

The setupResourceWatch loop at lines 357–368 retries fetchConfig forever. When two plugins enter this loop concurrently, the second completion's notifyDisconnected destroys the first plugin's watchers.

pkg/rancher-desktop/store/rddConnection.ts
      while (!rddState.config.currentContext) {
        try {
          await dispatch('rdd-connection/fetchConfig', {}, { root: true });
        } catch (error) {
          // If any error occurs during fetching of config, retry forever until
          // the backend is up.
          // TODO: Once we have diagnostics, emit one here so the user can
          // deal with it.
          commit('rdd-connection/SET_ERROR', error, { root: true });
          console.error(error);
          await new Promise(resolve => setTimeout(resolve, 1_000));
        }
      }

Fix: Deduplicate fetchConfig so concurrent calls return the same pending promise. Clear the cached promise in a finally block.

I2. waitForResources resolves before the initial list populates the cache Codex ¶

waitForResources treats watcher.loaded as "first list completed," but Watcher resolves that latch from onChange on the connect event. In ListWatch.doneHandler, CONNECT callbacks fire at line 180 before listFn runs and before addOrUpdateItems loads the cache. A slow first list lets waitForResources return early, so ensureAppStarted concludes no app exists and spams createApp/409.

pkg/rdd-client/cache.ts
    if (this.stopped) {
      // do not auto-restart
      return;
    }
    this.callbackCache[CONNECT].forEach((elt: ErrorCallback) => elt(undefined));
    if (!this.resourceVersion) {
      let list: KubernetesListObject<T>;
      try {
        const promise = this.listFn();
        list = await promise;
      } catch (err) {
        this.callbackCache[ERROR].forEach((elt: ErrorCallback) => elt(err));
        return;
      }
      this.objects = deleteItems(this.objects, list.items, this.callbackCache[DELETE].slice());
      this.addOrUpdateItems(list.items);
      this.resourceVersion = list.metadata ? list.metadata.resourceVersion || '' : '';
    }

waitForResources at lines 504–516 awaits watcherInfo.watcher.loaded, which resolves on the CONNECT event — before list data arrives.

pkg/rancher-desktop/store/rddConnection.ts
    async waitForResources(actionContext: ActionContext<State>, resources: ResourceNames<T>[]) {
      const { state } = actionContext;
      await state._watchersInitialized;
      await Promise.all(resources.map(async(resource) => {
        const watcherInfo = state._watchers[resource];
        if (!watcherInfo) {
          const error = new Error(`Action waitForResources(${ resource }) called before setupWatch`);
          console.error(error);
          throw error;
        }
        await watcherInfo.watcher.loaded;
      }));
    },

Fix: Move the CONNECT callback invocation in cache.ts to after the initial list block completes, or resolve Watcher.loaded from a separate post-list signal.

I3. ensureAppStarted exits permanently on transient create errors Claude ¶

Non-409 errors during createApp (transient 500, network timeout) cause an early return with no retry. The app remains permanently unstarted until the user reloads. The waitForResources retry loop at lines 75–87 handles connection failures well, but the create-and-patch phase has no equivalent resilience.

pkg/rancher-desktop/store/rdd.ts

Fix: Wrap the create-and-patch section in a retry loop with backoff for transient errors (5xx, network), or at minimum retry before giving up.

I7. unwatchResources may trigger spurious reconnect Gemini Codex ¶

When the last consumer unmounts, close() calls ListWatch.stop(), which aborts the in-flight fetch. In ListWatch.doneHandler, ERROR callbacks may fire before the stopped flag check, triggering the watcher's error handler and the reconnect path. Because setupResourceWatch on reconnect closes all watchers, this can cascade.

pkg/rancher-desktop/store/rddConnection.ts
        commit('SET__WATCHERS', {
          ...state._watchers,
          [resource]: {
            ...watcherInfo,
            refCount: count - 1,
          },
        } as any);
        if (count === 1) {
          watcherInfo.watcher.close();
        }

ListWatch.stop() at lines 86–90 sets stopped = true before aborting, and doneHandler checks this flag at line 176. The race is timing-dependent, not guaranteed.

pkg/rdd-client/cache.ts
  public stop(): Promise<void> {
    this.stopped = true;
    this._stop();
    return Promise.resolve();
  }

Fix: Guard doneFn to check whether the closed watcher is still the active watcher with a positive refcount, or add an intentionallyClosed flag in the Watcher class that suppresses error callbacks on explicit closure.

I8. Key collision in disconnectCallbacks for namespaces Gemini ¶

Both rdd.ts and container-engine.ts define a resource named namespaces. The disconnect callback key r.name collides: whichever plugin finishes last overwrites the other's callback. On disconnect, only the last-registered callback fires; the other watcher leaks.

pkg/rancher-desktop/store/rddConnection.ts
          await dispatch('rdd-connection/registerDisconnectCallback',
            {
              key:      r.name,
              callback: () => {
                watcher.close();
                dispatch('rdd-connection/registerDisconnectCallback', { key: r.name }, { root: true });
              },
            }, { root: true });

Fix: Include the store module name in the key (e.g., ${moduleName}/${r.name}) or use a unique ID per watcher instance.

Suggestions ¶

S1. BackendProgress shows blank indeterminate spinner Codex ¶

progressIndeterminate now keys off !this.running, but the progress feed (k8s-progress IPC) is commented out. Startup shows a blank indeterminate bar with empty labels instead of meaningful progress.

S2. ContainerInfo.vue uses onMounted instead of onBeforeMount Claude ¶

The watchResources docstring says "expected to be called in a component's onBeforeMount() hook." All other pages use beforeMount. ContainerInfo.vue uses onMounted instead. Functionally correct (the watcher is likely running from the parent page), but inconsistent with the documented convention.

S3. status getter returns a function, bypassing Vuex caching Claude ¶

The status getter at rdd.ts:49-54 returns a new function on every access. Vuex getters that return functions bypass caching. Currently only called from other getters, so impact is negligible.

S4. BackendProgress test suite entirely skipped Claude ¶

The entire meaningful test suite is wrapped in describe.skip at BackendProgress.spec.ts:42. The change to progressIndeterminate has no test coverage.

S5. Incomplete mockModules default Claude ¶

The default mock for @pkg/entry/store at mockModules.ts:6-13 provides only mapTypedGetters. Components using mapTypedState, mapTypedMutations, or mapTypedActions get undefined. Works for current tests but incomplete as a reusable default.

S6. Unnecessary polling loop for App resource Gemini ¶

The while loop at rdd.ts:93-123 spams createApp every 100ms while waiting for getters.app to update via the async watch. The app name is hardcoded to 'app' in the same function. The loop could be replaced with a single createApp call (catching 409) and using the literal name in patchApp.

S7. Dead created getter Claude ¶

The created getter at rdd.ts:55-57 is defined but never consumed by any component or action.

S8. app getter predicate misleading Claude ¶

find(app => !!app) at rdd.ts:47 filters falsy values, but Kubernetes resource objects are always truthy. state.apps?.[0] is more direct.

S9. setCurrentNamespace replaces watch callback on reconnect Claude ¶

setCurrentNamespace calls setupResourceWatch with a fresh callback, replacing the plugin's original doneFn closure. All subsequent automatic reconnects permanently use the namespace-change callback. Both callbacks are functionally equivalent today, but the coupling is fragile.

S10. usePassthroughURL uses module-global flag Codex ¶

The systemConfigMapsWatched boolean at passthrough.ts:19 is process-global rather than store-owned. Brittle in tests and HMR-like flows. Works correctly with the "watch once, never unwatch" pattern, but would be more robust as store state.

S11. listFn/watch fieldSelector divergence Claude ¶

listFn at rddConnection.ts:381-393 evaluates selectors eagerly; the watch at lines 421-423 evaluates them lazily via functions. Both close over the same actionContext, so they read the same reactive getters in practice. The inconsistency is a maintainability concern — a future change could introduce a filter mismatch.

S12. setCurrentNamespace resets latch Claude ¶

setupResourceWatch replaces _watchersInitialized with a new unresolved latch at rddConnection.ts:374. During a namespace change, concurrent watchResources or unwatchResources calls block until setupResourceWatch completes, including the config-fetch retry loop. Downgraded from Important: config is already valid during namespace changes, so the retry loop does not execute.

Design Observations ¶

Concerns

  1. (in-scope) The watch lifecycle has no semantic distinction between intentional close and backend disconnect. ListWatch.stop() and a backend-initiated disconnect both fire the same error path, causing cascading reconnect logic. Moving that distinction into ListWatch or Watcher would eliminate an entire class of bugs. Codex Gemini
  2. (in-scope) Two competing sources of truth for runtime settings: preferences and app.spec. Seeding App from preferences, or introducing a single getter that resolves the authoritative value with fallback rules, would eliminate the mixed-state problem behind I9 and simplify future consumers. Codex
  3. (in-scope) ensureAppStarted mixes concerns: waiting for resources, creating the app, polling for the app in the store, and patching it to running. A more robust approach would use a Vuex store subscription or a watcher on getters.app instead of the 100ms polling loop. Claude

Strengths

  1. The refcounted watchResources/unwatchResources API cleanly handles overlapping component lifecycles. When two components watch the same resource, the watcher runs as long as either is active. Claude Codex Gemini
  2. The setHeaderOptions middleware approach for overriding Content-Type avoids modifying generated code and composes well with other middleware. Claude Codex
  3. The path field as a function (namespace: string) => string allows namespace-scoped watch paths to use the correct namespace from connection state, rather than requiring resources to know about namespacing at definition time. Claude
  4. Lazy fieldSelector/labelSelector evaluation via functions in ListWatch elegantly solves stale-selector bugs when Vuex state changes. Gemini
  5. The Latch synchronization pattern for _watchersInitialized cleanly separates the "setup done" signal from the "data loaded" signal, allowing callers to wait at the right granularity. Claude

Testing Assessment ¶

  1. No tests for ensureAppStarted — This action has multiple code paths (wait/retry, create/409, patch) and error handling that should have unit tests. This is the riskiest untested code in the PR.
  2. No tests for refcounted watchResources/unwatchResources — The refcount increment/decrement logic, invalid-refcount recovery, and interaction with _watchersInitialized are all untested.
  3. No tests for setupResourceWatch reconnect behavior — The reconnect path in doneFn (clear config, re-fetch, re-setup) has multiple async steps and error handling that could regress.
  4. BackendProgress.spec.ts entirely skipped — The test suite validating progress bar behavior is wrapped in describe.skip. The change to progressIndeterminate is untested.
  5. No test for waitForResources pre-list timing — The "app already exists" path where ensureAppStarted observes the existing object is not exercised.
  6. StatusBar test does not cover app being undefined — The initial state where kubernetesEnabled returns false and containerEngine returns 'unknown' is not verified.

The waitForResources doc comment promises it waits for the initial list to load, but the implementation does not yet satisfy that contract (I2) — update the comment once the timing is fixed, or fix the implementation to match.
