## Executive Summary

Round 2 adds two new commits on top of the round 1 head: `Container-engine: Change state setting` (renames `containerSetState` → `containerRequestAction`, switches from `spec.state` to the `containers.rancherdesktop.io/action` metadata annotation, and broadens the action enum to `start`/`stop`/`pause`/`unpause`/`restart`) and `Store: rdd: remove unused statuses` (drops the unreferenced `created` and `running` getters). These are exactly the changes round 1's I1 and S1 asked for, and they cleanly resolve both findings. The migration also correctly keeps the explicit `MergePatch` content-type override so the JSON-patch default in the generated client does not kick in. The new gap exposed by the API migration is one Claude raised: actions are now asynchronous, the daemon reports their outcome through `status.lastAction.state` / `status.lastAction.error`, and the renderer never reads either field — a Stop that fails server-side leaves no UI trace. The remaining suggestions are minor: the `state`-named action parameter that should be `action`, a hard-coded annotation key string, a silently-dropped non-binary WebSocket frame, a now-stale `pkg/rdd-client/README.md` prerequisite section, and a pre-existing buffering concern in `ContainerLogs.vue` that this PR does not change but Gemini surfaced.

**Structure.** 1 Important, 5 Suggestions. The Important finding was raised by Claude only; the daemon-async-feedback gap is non-obvious because the regenerated model is generated correctly — the renderer simply does not consume the new fields yet.

## Important Issues

I1. **`lastAction.state === 'Failed'` outcome never reaches the user** — `pkg/rancher-desktop/store/container-engine.ts:111-139` [Claude Opus 4.7]

```ts
return client.patchNamespacedContainer(
  {
    name:            container.metadata!.name!,
    namespace:       container.metadata!.namespace!,
    body,
    fieldValidation: 'Strict',
  },
  RDDClient.setHeaderOptions('Content-Type', RDDClient.PatchStrategy.MergePatch),
).catch((err: Error) => {
  commit('SET_ERROR', { error: err, source: 'containers' });
});
```

Under the previous `spec.state` model the patch carried the desired state and the daemon could (in principle) reject it synchronously through the HTTP response. Under the new annotation-based model the patch only writes the request annotation, so the HTTP path always succeeds; the daemon then reports the outcome asynchronously through `status.lastAction`.

The regenerated `IoRancherdesktopContainersV1alpha1ContainerStatusLastAction` (`pkg/rdd-client/gen/models/IoRancherdesktopContainersV1alpha1ContainerStatusLastAction.ts:18-39`) makes both fields explicit: `action`, `state` (`Succeeded` | `Failed`), `error`, `observedAt`, `completedAt`. A grep for `lastAction` across `pkg/rancher-desktop/` finds zero references — neither the action dispatcher in `containerSetState` (now `containerRequestAction`), nor any watcher, nor any UI component reads it. A user who clicks Stop on a container that the daemon then fails to stop sees no error banner, no state transition, and no log entry; the UI just keeps rendering the container as running.

Fix: surface `lastAction.error` through the existing `SET_ERROR` channel when the most-recently-requested container's `status.lastAction.action` matches the dispatched action and `status.lastAction.state === 'Failed'`. A minimal first cut is to remember the last `(name, namespace, action)` tuple inside `containerRequestAction`, and add a watcher (or `resourceWatchActions`-driven reactor) on the container that compares the next status update against that tuple. Bonus: also clear the previous error on success so the banner does not stick.

We classify this Important rather than Critical because the failure surface is not new — pre-PR, the `spec.state` patch was rejected on the wire by the new daemon and `containerSetState` already had no progress feedback path. This PR is the natural place to wire the new feedback channel in alongside the new request channel.

S5. **`buffer` can grow without bound while initial logs stream continuously** — `pkg/rancher-desktop/components/ContainerLogs.vue:13-26, 232-267` [Gemini 3.1 Pro]

```vue
<loading-indicator
  v-if="!container || waitingForInitialLogs"
  ...
/>
<div
  v-else
  ref="terminalContainer"
  ...
/>
```

The terminal container only mounts (and the `terminalContainer` watch fires, creating the xterm `Terminal` and draining `buffer`) once `waitingForInitialLogs` flips to false. The `open` handler arms a 500 ms reveal timer; every incoming message clears that timer and re-arms a 200 ms one. While messages keep arriving faster than 200 ms apart, `waitingForInitialLogs` stays true, the terminal never mounts, and `buffer.push(event.data)` accumulates every chunk. For a container with hundreds of MB of historical logs streamed in a continuous burst, this can hold the whole backlog in renderer memory before xterm sees the first byte.

The behavior pre-dates this PR (the same pattern existed with `buffer = ''` and `buffer += event.data`), so we mark this **gap, pre-existing** rather than a regression — keep it on the radar but it does not block the PR. A cap (e.g., bounded ring buffer, or floor the reveal timer instead of resetting it) would close the long-tail risk.

## Design Observations

### Strengths

- **Annotation-based action over declarative state** *(in-scope)* [Claude Opus 4.7]. The renderer-side action union (`'start' | 'stop' | 'pause' | 'unpause' | 'restart'`) mirrors the daemon's `IoRancherdesktopContainersV1alpha1ContainerStatusLastActionActionEnum` 1:1 (`pkg/rdd-client/gen/models/IoRancherdesktopContainersV1alpha1ContainerStatusLastAction.ts:84-90`), so a future server-side action addition surfaces as a TypeScript widening rather than a runtime mismatch — assuming the renderer also adopts the constant from S2.
- **Explicit `MergePatch` content-type override survives the migration** *(in-scope)* [Codex GPT 5.5]. The `RDDClient.setHeaderOptions('Content-Type', RDDClient.PatchStrategy.MergePatch)` call at `pkg/rancher-desktop/store/container-engine.ts:135` keeps the generated client's default `application/json-patch+json` from kicking in for an object-shaped patch body — exactly the trap captured in `deep-review-context.md`.
- **Buffer-of-chunks instead of buffer-of-bytes** *(in-scope)* [Claude Opus 4.7]. `let buffer: ArrayBuffer[] = []` (`ContainerLogs.vue:66`) preserves frame boundaries, avoids any string transcoding, and never has to worry about cutting a multibyte character in half. The drained loop at lines 177-180 is the minimal correct shape.
- **Single `Settled` condition collapses two getters** *(in-scope)* [Claude Opus 4.7, Gemini 3.1 Pro]. The daemon now publishes "running and not transitioning" explicitly, so `BackendProgress.vue` no longer has to compose its own signal.

### Strengths

- **Buffer-of-chunks instead of buffer-of-bytes** — `let buffer: ArrayBuffer[] = []` (`ContainerLogs.vue:66`) is the right model for a binary protocol: it preserves frame boundaries, avoids any string/utf-8 transcoding, and never has to worry about cutting a multibyte character in half. - **Annotation-based action over declarative state** — the cleanly-typed action enum (`'start' | 'stop' | 'pause' | 'unpause' | 'restart'`) on the renderer side mirrors the server enum 1:1 (see `IoRancherdesktopContainersV1alpha1ContainerStatusLastActionActionEnum` at lines 88-94 of the new model), so a future server-side action addition surfaces immediately as a TypeScript error rather than a runtime mismatch — assuming the renderer also adopts the constant suggested in S2.

#### Important Issues

I1. **Unbounded memory buffer before terminal mounting** — `pkg/rancher-desktop/components/ContainerLogs.vue:245-249` (important, gap)

```typescript
      const t = terminal;
      if (!t) {
        buffer.push(event.data);
        return;
      }
```

The component delays mounting the `terminalContainer` until the log stream pauses for at least 200ms (`revealTimeout` logic on lines 259-269). During this period, all incoming logs are appended to `buffer` in memory. If a container has a large historical log (e.g., hundreds of megabytes), this buffer will grow unbounded, consuming excessive memory. When the terminal finally mounts, the component executes a synchronous `for` loop over the entire array to write chunks to xterm.js, which can freeze the Electron renderer process.

Fix: Rather than delaying the terminal mount, mount it immediately and write chunks directly to xterm.js, which manages its own internal queue efficiently. If visual flicker is a concern, hide the terminal container with CSS (e.g., `visibility: hidden` or `opacity: 0`) until the initial log burst completes.
