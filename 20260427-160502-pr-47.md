## Executive Summary

Round 2 rebases the prior "namespace from app" PR onto a substantially rewritten watch path. The architectural moves are good: namespace tracking moved into `rdd-connection` (a new `addNamespacedResource` registry plus a `SET_NAMESPACE` mutation), `rewatchResources` action replaces full-`setupResourceWatch` re-entry on namespace change, `Watcher.start()` recreates the inner `ListWatch` and uses `Object.is(watcher, this.#watcher)` stale-watcher checks, and the `rdd` module's unused `configMaps` resource is dropped. Round 1's I2 (rdd asymmetry), I3 (concurrency in `setupResourceWatch`), and I4 (transient-undefined rebind) are addressed by these moves.

What landed less cleanly: the `error` handler on the inner `ListWatch` now calls `clearTimeout(this.#restartTimeout)` *before* the stale-watcher check, so a deferred error from a closed watcher cancels a still-pending 429 restart on the live watcher; the `callback` parameter type widened from a strict `ResourceNames<T>` union to `ResourceNames<T>[number]`, which evaluates to plain `string` and silently loses callback-arg type safety; and the round-1 fallback-when-`spec.namespace`-undefined concern returned in a new shape (the rdd-side `if (newNamespace)` guard now drops legitimate `undefined → 'default'` transitions). Several round-1 Suggestions remain unaddressed and resurface here (Images.vue stale `kubeNamespace` mapping, redundant primitive equality guard, missing JSDoc on `kubernetesNamespace`).

Structure: 0 critical, 3 important, 10 suggestions, 1 design observation.

I1. **`kubernetesNamespace` getter does not apply the documented `'default'` fallback** — `pkg/rancher-desktop/store/rdd.ts:48-51,151-153` [Codex GPT 5.5, Gemini 3.1 Pro]

The generated `IoRancherdesktopAppV1alpha1AppSpec.ts:24` documents that `spec.namespace` "Defaults to `default` if not specified." The repo-context note for this codebase explicitly says callers that depend on `app.spec.namespace` need an explicit fallback. The current code does the opposite: the getter returns the raw optional, and the `if (newNamespace)` guard silently drops every `undefined` observation.

That's fine for the locally-created App because `ensureAppStarted` writes `spec.namespace: 'rancher-desktop'` explicitly (`rdd.ts:100`), but two paths still hit `undefined`:

1. An externally-managed App whose `spec.namespace` is omitted relies on the server's default. Whether the API server fills the field on read depends on the CRD's `default` schema being applied; if it isn't, the wire JSON omits it and the renderer parks at the initial `'default'` (rddConnection.ts:36) without ever observing a transition.

This is a re-raise of round-1 I1; the author chose not to fix it then and `mook-as` flagged this round as nit-picking. Recording it because the repo-context convention names it (treat `app.spec.namespace` as `string | undefined` and apply an explicit fallback), and the fix is a one-liner. Gemini called this Critical citing `omitempty` semantics; downgraded to Important — `omitempty` is a Go encoder behavior that doesn't fire when the server has already filled in the default, so the runtime impact is narrower than Gemini described, but the contract violation is real.

I2. **`clearTimeout` runs before the stale-watcher check, can cancel a live 429 restart** — `pkg/rancher-desktop/store/rddConnection.ts:640-661` [Claude Opus 4.7]

```ts
watcher.on('error', (err) => {
  clearTimeout(this.#restartTimeout);
  if (!Object.is(watcher, this.#watcher)) {
    // This error is from a stale watcher; ignore it.
    return;
  }
  this.#loaded.reset();
  this.#loaded.catch(() => { /* ignore */ });
  if (Object.is(err, errorManuallyStopped)) {
    return;
  } else if (err.statusCode === 429) {
    ...
    this.#restartTimeout = setTimeout(() => this.start(), delay * 1_000);
    return;
  }
  ...
});
```

`#restartTimeout` is a per-`Watcher` field, but the `error` handler is the *only* event handler that touches `this.#restartTimeout` *before* the stale-check at line 642. The `change`, `connect`, and `start().catch` handlers (lines 628-639, 671-678) all return early when `!Object.is(watcher, this.#watcher)` and never mutate watcher state. The `error` handler is the outlier.

Concrete sequence:

1. Inner `ListWatch` A is running.
2. A is closed by `start()`'s line 618 (`this.#watcher?.stop(errorManuallyStopped)`) when the namespace changes; the abort propagates asynchronously.
3. Line 627 assigns `this.#watcher = B`.
4. B's `start()` runs, hits a 429, sets `this.#restartTimeout = setTimeout(() => this.start(), delay)`.
5. A's `'error'` event finally fires (with `errorManuallyStopped` as the reason).
6. The handler executes `clearTimeout(this.#restartTimeout)` — clearing **B's** restart — *then* `!Object.is(A, B)` is true and returns.
7. B's restart never fires; the watcher is silently parked. No further `'error'`, `'change'`, or `'connect'` event will trigger it back to life.

The window is small but the mode is "no further trigger" — once parked, the watcher only recovers when the next external `rewatchResources` arrives (a namespace change). Pages stay loading indefinitely until then.

Fix: move the `clearTimeout` after the stale-check, so a stale watcher's deferred error never touches the live watcher's restart timer.

```diff
 watcher.on('error', (err) => {
-  clearTimeout(this.#restartTimeout);
   if (!Object.is(watcher, this.#watcher)) {
     // This error is from a stale watcher; ignore it.
     return;
   }
+  clearTimeout(this.#restartTimeout);
   this.#loaded.reset();
   this.#loaded.catch(() => { /* ignore */ });
```

I3. **`ResourceNames<T>[number]` widens callback signature to plain `string`** — `pkg/rancher-desktop/store/rddConnection.ts:312-314,429` [Gemini 3.1 Pro, Claude Opus 4.7]

```ts
interface ResourceWatchActionsOptions<T extends readonly ResourceTypeLike[]> {
  /** Callback that is invoked when an error occurs. */
  callback?: (error: Error, resourceName: ResourceNames<T>[number]) => void,
}
```

`ResourceNames<T>` is already a string-literal union built by ending the mapped type with `}[number]` (lines 236-241). Indexing a string-literal union with `[number]` evaluates to the primitive `string` (TypeScript treats string literals as char-indexable, and the `[number]` index of any string is `string`). So the callback's `resourceName` parameter is now plain `string`, not the precise union it was pre-PR.

This is a regression of the API surface that round 1 established. The change at line 429 (`resourceOptions.callback?.(error, r.name)`) was probably the trigger — `r.name` widens to `string` inside the `for (const r of resources)` loop, so the original `ResourceNames<T>` annotation no longer matched without a cast. The cheap-looking fix at 313 silently dropped the type narrowing for every consumer.

Concrete impact: `container-engine.ts:253` writes `(error: Error, source) => store.commit('container-engine/SET_ERROR', { error, source })`. Pre-PR, `source` was inferred as `'containers' | 'images' | 'namespaces' | 'volumes'`, matching `SET_ERROR`'s `{ source: resourceNames }` payload. Post-PR, `source` is `string`, and the only thing keeping the commit call from compile-erroring is the `payload?` looseness in `MutationsType<>`.

Gemini called this Important; Claude called it Suggestion. Promoting because it is a quiet regression of a contract the prior PR added, the surface lives in a public-ish helper (`resourceWatchActions`), and the fix is one cast.

Fix: revert the type and add the cast at the callsite.

```diff
 interface ResourceWatchActionsOptions<T extends readonly ResourceTypeLike[]> {
   /** Callback that is invoked when an error occurs. */
-  callback?: (error: Error, resourceName: ResourceNames<T>[number]) => void,
+  callback?: (error: Error, resourceName: ResourceNames<T>) => void,
 }
```

```diff

-                resourceOptions.callback?.(error, r.name);
+                resourceOptions.callback?.(error, r.name as ResourceNames<T>);
```

## Design Observations

### Strengths

- *(in-scope)* Recreating the inner `ListWatch` in every `Watcher.start()` (lines 619-680) and gating callbacks on `Object.is(watcher, this.#watcher)` is exactly the right shape for repeated rewatches — it avoids the long-standing `ListWatch.start()` re-use fragility and makes stale events safe to ignore. [Codex GPT 5.5, Claude Opus 4.7]
- *(in-scope)* Promoting `path`, `labelSelector`, and `fieldSelector` to thunks on the `Watcher` (lines 412, 449-450) lets each `start()` re-evaluate against current store state, so the rewatch flow works without recreating the wrapping `Watcher`. [Claude Opus 4.7]
- *(in-scope)* Tracking namespaced resources in `rdd-connection.namespacedResources` (a `Record<string, Set<string>>`) and dispatching `rewatchResources` per module on namespace change is cleaner than the prior disconnect-callback indirection, and isolates per-watcher reconnect inside `doneFn`. [Claude Opus 4.7]
- *(in-scope)* The `Latch.settled` accessor (`pkg/rancher-desktop/utils/latch.ts:24-25,90-94`) is a minimal addition wired correctly into `resolve`/`reject`/`reset`, and the `setupResourceWatch` "called more than once" guard that uses it is the right shape. [Claude Opus 4.7]
- *(in-scope)* Multi-line regex fix in `pkg/rdd-client/watch.ts` — switching from `/^(.*?)\r?\n(.*?)$/m` to `/^(.*?)\r?\n(.*)$/s` resolves a chunking bug where multiple JSON events in a single buffer read were swallowed because `.` in non-`s` mode does not match newlines, so `(.*?)` after the newline could not capture the remainder. [Gemini 3.1 Pro]
- *(in-scope)* Dynamic `listFn` discovery in `setupResourceWatch` (lines 383-409) — picking `listNamespaced<Type>` vs `list<Type>` based on the client shape — removes the per-resource `list:` boilerplate across `container-engine.ts` and `rdd.ts` and centralizes the namespaced/cluster-scoped distinction. [Gemini 3.1 Pro]
- *(in-scope)* `Plugin<RootState>` typing across all four modules (round 1's I2-related hygiene) is uniform and removes the per-module `Plugin<ModuleState>` divergence. [Claude Opus 4.7]

### Concerns

- *(in-scope)* **Periodic-reconnect behavior changed materially with the new `watch.ts` timeout semantics** [Claude Opus 4.7]

  Pre-PR, `AbortSignal.timeout(this.getRequestTimeoutMS())` at the original `pkg/rdd-client/watch.ts` used a random 5–10 minute window applied to the entire fetch lifetime; on fire, the previous `try/catch` turned a `timeoutSignal.aborted` into `done(null)` — a graceful close that triggered `ListWatch` auto-restart. That matched the Kubernetes client-go pattern of forcing periodic reconnects to resume from a fresh resourceVersion.

  Post-PR (`pkg/rdd-client/watch.ts:64-70,141-143`), the timeout is created with `setTimeout` and cleared in a `finally` block. Once the body-streaming IIFE launches, the `finally` clears the timer, so the timeout effectively gates only the headers-arrival window of the initial fetch. There is no longer a client-side periodic reconnect; if the daemon's body socket silently stalls, the read just hangs.

  For local IPC this is likely fine, and the `error`-path reconnect still recovers from drops, but the random 5–10 minute window is now a vestige and obscures the change in semantics. Two options:
  1. Shorten the initial-connect timeout to something HTTP-sized (e.g. 30 s) and rename `getRequestTimeoutMS` accordingly.
  2. Restore the periodic graceful-close behavior — re-arm the timeout when streaming starts and treat its firing as a normal end-of-stream.

## Testing Assessment

No automated tests cover `pkg/rancher-desktop/store/rddConnection.ts`, `pkg/rdd-client/watch.ts`, or the namespace-change pipeline. **I1. `clearTimeout` runs before stale-watcher check, can cancel a live restart** — `pkg/rancher-desktop/store/rddConnection.ts:640-668` (important, regression)

```ts

  if (!Object.is(watcher, this.#watcher)) {
    // This error is from a stale watcher; ignore it.
    return;

    return;
```

`#restartTimeout` is a per-Watcher field, so when an event from an old internal `ListWatch` fires after a new one has been installed, the handler clears the timeout *before* the `Object.is` stale check (line 641). Concretely:

1. Internal `ListWatch` A is running.
2. A's request is aborted (e.g., `close()` from `rewatchResources` because of a namespace change), but its `'error'` event has not yet been delivered.
3. `start()` immediately installs `ListWatch` B and assigns `this.#watcher = B`.
4. B starts, hits a 429, and sets `this.#restartTimeout = setTimeout(() => this.start(), …)` (line 660).
5. A's deferred `'error'` event finally fires; the handler executes `clearTimeout(this.#restartTimeout)` (line 641) — clearing **B's** legitimate restart — *then* sees that A is stale and returns.

The other event handlers (`change`, `connect`, `start().catch`) at lines 628-639 and 671-679 already perform the stale-check first; the `error` handler is the outlier.


**Periodic-reconnect behavior changed materially with the new timeout semantics** — `pkg/rdd-client/watch.ts:67-70, 139-143` *(in-scope)*

The previous `AbortSignal.timeout(this.getRequestTimeoutMS())` applied to the entire fetch lifetime (5–10 minutes), and a fired timeout was caught and turned into `done(null)` — a graceful close that triggers `ListWatch` auto-restart. That mirrored the Kubernetes client-go pattern of forcing periodic reconnects to resume from a fresh resourceVersion. The new code keeps the 5-10 minute random duration but `clearTimeout`s it in `finally` (line 142), so the timeout effectively gates only the headers-arrival window of the initial fetch — once the body-streaming IIFE is launched the timeout is cancelled. There is now no client-side periodic reconnect; if the daemon's body socket silently stalls, the read just hangs.

For local IPC that's likely fine, and the reconnect on `error` paths still recovers from drops, but the random 5-10 minute window for "initial connect" is a vestige and obscures the change in semantics. Consider either (a) shortening the initial-connect timeout to something HTTP-sized (e.g. 30 s) and renaming `getRequestTimeoutMS` accordingly, or (b) keeping the periodic graceful close (re-arm the timeout when streaming starts and treat its firing as a normal end-of-stream, as the old code did).

The main correctness gap is that the new App namespace getter does not apply the server-side default, so an omitted `spec.namespace` leaves watchers on the previous namespace. I also found two smaller cleanup/error-handling issues around 429 handling and a stale namespace mapping.

### [Gemini] — Original

### Executive Summary
This PR refactors how the Kubernetes connection watcher determines the target namespace, deriving it from the `App` custom resource rather than hardcoding `'rancher-desktop'`. It consolidates watcher startup logic, simplifies resource registration by automatically resolving namespaced versus cluster-scoped list functions, and improves reconnect resiliency. However, a missing default fallback leaves the UI vulnerable to becoming permanently stuck if the namespace is reverted to the default, and an overly broad type signature inadvertently defeats compile-time checks on the resource APIs.

### Findings

#### Critical Issues
**C1. Missing fallback for `app.spec.namespace` causing missed updates** — `pkg/rancher-desktop/store/rdd.ts:149-154` (critical, regression)

```typescript
  // When the app namespace changes, set it on the connection state.
  function(store) {
    store.watch(
      (_state, getters) => getters['rdd/kubernetesNamespace'],
      (newNamespace: string | undefined) => {
        if (newNamespace) { // Ignore empty/unset; not valid for state.
          store.commit('rdd-connection/SET_NAMESPACE', newNamespace);
        }
      },
    );
  },
```

The CRD documents that `spec.namespace` defaults to `"default"` server-side. Because Kubernetes APIs omit fields that match their default (`omitempty`), the generated client will evaluate `app.spec.namespace` as `undefined` when the app resides in the `"default"` namespace. The defensive guard `if (newNamespace)` silently skips the update. If a user reverts the app's namespace from a custom value back to the default, this getter evaluates to `undefined`, the update is blocked, and the `rdd-connection` state remains permanently stuck pointing at the old custom namespace.

Fix: Provide an explicit fallback instead of ignoring `undefined`.

```diff
-      (newNamespace: string | undefined) => {
-        if (newNamespace) { // Ignore empty/unset; not valid for state.
-          store.commit('rdd-connection/SET_NAMESPACE', newNamespace);
-        }
-      },
+      (newNamespace: string | undefined) => {
+        store.commit('rdd-connection/SET_NAMESPACE', newNamespace || 'default');
+      },
```

#### Important Issues
**I1. Widened resource name type bypasses compiler checks** — `pkg/rancher-desktop/store/rddConnection.ts:312-314` (important, regression)

```typescript
interface ResourceWatchActionsOptions<T extends readonly ResourceTypeLike[]> {
  /** Callback that is invoked when an error occurs. */
  callback?: (error: Error, resourceName: ResourceNames<T>[number]) => void,
}
```

The PR widens the `callback` signature from `ResourceNames<T>` to `ResourceNames<T>[number]`. Because `ResourceNames<T>` evaluates to a string literal union (e.g., `'containers' | 'images' | 'volumes'`), indexing a string union with `[number]` resolves to its numeric index signature, evaluating to the primitive `string`. This unintentionally allows any arbitrary string to be passed, defeating the type-safety of the resource watcher API. The change was likely made to avoid an internal cast, but it breaks compile-time enforcement for consumers.

Fix: Revert the callback signature to use the strict union, and use a cast internally where `r.name` is evaluated.

```diff
-  callback?: (error: Error, resourceName: ResourceNames<T>[number]) => void,
+  callback?: (error: Error, resourceName: ResourceNames<T>) => void,
```

And in `setupResourceWatch` (line 429):

```diff

-                resourceOptions.callback?.(error, r.name);
+                resourceOptions.callback?.(error, r.name as ResourceNames<T>);
```

### Design Observations

#### Strengths
- The refactoring of `pkg/rdd-client/watch.ts` to use `/^(.*?)\r?\n(.*)$/s` resolves a hidden chunking bug where multiple JSON events delivered in a single buffer read were swallowed due to the non-matching behavior of the `m` flag against `.` capturing.
- The dynamic `listFn` discovery based on the client shape (`listNamespaced*` vs. `list*`) in `setupResourceWatch` removes a lot of boilerplate across store modules and centralizes the distinction nicely.

### Testing Assessment
1. **Fallback namespace transitions**: There is no explicit test verifying that reverting the App namespace to default (producing an omitted/undefined API field) correctly falls back and updates the Vuex store namespace back to `"default"`.
2. **Watch event chunking**: Although the JSON event extraction regex was corrected to handle multiple events per chunk, there is no unit test confirming that an active watch stream processes a combined `buffer + newline + buffer + newline` chunk correctly without dropping the remainder.
