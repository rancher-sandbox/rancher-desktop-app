## Executive Summary

This PR replaces `rdctl paths` with `rdd service paths` and reshapes the
`Paths` interface around RDD-provided keys (`dir`, `log_dir`, `cache`,
`config`, …). The migration is substantially incomplete: several
production and test files still reference the old `Paths` properties
(`appHome`, `deploymentProfileUser`, `getRdctlPath`), one property name
silently changes meaning (`config`: settings dir → kubeconfig file), and
the new `paths.resources` getter no longer appends the `resources/`
subdirectory that `electron-builder` packages assets under, breaking
icon, preload, and tray-icon resolution in packaged builds. Several
unmigrated callers will fail TypeScript compilation; the rest will
break at runtime. Structure (Critical 4, Important 6, Suggestions 6).

C3. **`paths.config` silently changes meaning from settings directory to kubeconfig file** — `pkg/rancher-desktop/utils/paths.ts:19-20` [Claude Opus 4.7, Codex GPT 5.5, Gemini 3.1 Pro]

```typescript
/** RDD: Kubernetes connection configuration file. */
readonly config:        string;
```

Pre-PR, `paths.config` was a directory holding `settings.json`. The
new `RDDPaths.config` is documented as the kubeconfig **file**.
The type stays `string`, so TypeScript catches nothing, but every
caller that joins `'settings.json'` onto `paths.config` now produces
a path like `~/.rd/config/settings.json` (creating `settings.json`
inside what is supposed to be a file).

Affected call sites:

- `pkg/rancher-desktop/config/commandLineOptions.ts:80,90` — error
  messages reference `${ join(paths.config, 'settings.json') }`.
- `e2e/utils/TestUtils.ts:131-136` — calls `fs.mkdirSync(paths.config)`
  and writes `settings.json` there.
- `e2e/utils/ProfileUtils.ts:26,103` — reads `path.join(paths.config, 'settings.json')`.

Fix: rename the RDD field at the type boundary (e.g., `kubeconfig` or
`connection_config`) and reinstate a separate app-level `config` (or
`configDir`) that returns the platform-specific settings directory.
This change keeps the JSON contract with `rdd` clean and prevents
silent semantic conflicts on the renderer side.

C4. **`paths.resources` is missing the `resources/` suffix in production builds** — `pkg/rancher-desktop/utils/paths.ts:142-149` [Codex GPT 5.5]

```typescript
get resources() {
  if (process.env.NODE_ENV === 'production') {
    return process.resourcesPath;
  }
  // When under test, we do not have `process.resourcesPath`; use a fallback.
  return process.resourcesPath ?? path.join(process.cwd(), 'resources');
},
```

`packaging/electron-builder.yml:10-11` packages the local `resources/`
directory into the Electron `Resources` folder via `extraResources`,
so packaged builds layout assets at `<process.resourcesPath>/resources/...`.
`scripts/package.ts:97` confirms this: `path.join(context.appOutDir, 'resources/resources/linux/${ leaf }')`.
Pre-PR, `rdctl paths` returned `<resourcesPath>/resources` for the
`resources` field (`src/go/rdctl/pkg/paths/paths_test.go:22`:
`assert.Equal(t, filepath.Join(dir, "resources"), actual)`). The new
getter omits that suffix.

Every existing consumer joins paths onto `paths.resources` expecting
the suffix to be there:

- `background.ts:113` — `path.join(paths.resources, 'icons', 'logo-square-512.png')`
- `pkg/rancher-desktop/window/index.ts:235` — `path.join(paths.resources, 'preload.js')`
- `pkg/rancher-desktop/main/tray.ts:113-117,122-125` — tray icons

In a packaged build this resolves to `<resourcesPath>/icons/...`
instead of `<resourcesPath>/resources/icons/...`, so all icons,
the renderer preload, and the tray badge silently miss.

The new `paths.spec.ts:155-164` test happens to assert
`actual.resources === undefined` when `process.resourcesPath` is
unset; it never asserts the packaged `resources/resources` layout.

Fix:

```diff
 get resources() {
   if (process.env.NODE_ENV === 'production') {
-    return process.resourcesPath;
+    return path.join(process.resourcesPath, 'resources');
   }
   // When under test, we do not have `process.resourcesPath`; use a fallback.
   return process.resourcesPath ?? path.join(process.cwd(), 'resources');
 },
```

Add a packaged-path test that reflects the `electron-builder` layout.

I2. **`paths.resources` typed `string` but can be `undefined` in production** — `pkg/rancher-desktop/utils/paths.ts:142-149` [Claude Opus 4.7]

```typescript
get resources() {
  if (process.env.NODE_ENV === 'production') {
    return process.resourcesPath;
  }
  return process.resourcesPath ?? path.join(process.cwd(), 'resources');
},
```

`Paths.resources` is typed `string` (line 44), but the production branch
returns `process.resourcesPath` directly with no guard. The new test at
`paths.spec.ts:155-164` asserts `actual.resources === undefined` when
`process.resourcesPath` is unset — i.e., the undefined branch is
documented behavior. Every existing caller feeds the value into
`path.join`, which throws `TypeError: Path must be a string. Received
undefined` on first access.

In packaged Electron `process.resourcesPath` is always set, so this is
latent rather than active; combined with C4, however, the production
branch needs a defensive guard regardless. Either tighten the return
type to `string | undefined` and update each caller, or throw with a
clear message:

```diff
   get resources() {
-    if (process.env.NODE_ENV === 'production') {
-      return process.resourcesPath;
+    if (process.env.NODE_ENV === 'production') {
+      if (!process.resourcesPath) {
+        throw new Error('process.resourcesPath is not set in production');
+      }
+      return path.join(process.resourcesPath, 'resources');
     }
```

I3. **`cachedRDDPath` persists across tests and never re-validates** — `pkg/rancher-desktop/utils/paths.ts:51-88` [Claude Opus 4.7]

```typescript
let cachedRDDPath: string | undefined;
...
if (useCached && cachedRDDPath) {
  return cachedRDDPath;
}
cachedRDDPath = (() => { ... })();
```

The module-level cache survives between Jest tests: every `getRDDPath(false)`
call in `paths.spec.ts` writes the cache, so a later default-cached
caller sees stale state. The function also never re-checks that the
cached path still resolves — a user who replaces or removes RDD
between calls keeps the old path forever.

Fix: drop the cache (a single `accessSync` is cheap), expose a
`resetCache()` helper for tests, or reset the cache in
`beforeEach`/`afterEach` in `paths.spec.ts`.

I5. **`getPaths()` swallows the underlying cause when returning the fallback Proxy** — `pkg/rancher-desktop/utils/paths.ts:242-272` [Claude Opus 4.7]

```typescript
} catch (cause) {
  if (cause instanceof UnsupportedPlatformError) { throw cause; }
  return new Proxy({} as Paths, {
    get(target, prop) {
      ...
      throw new Error(`Unable to determine path for ${ String(prop) }: ${ String(cause) }`, { cause });
    },
  });
}
```

The catch collapses all causes (RDD missing, RDD crashed, RDD returned
bogus JSON, RDD returned a non-zero status) into a single Proxy that
defers throwing. Construction emits no log line and no telemetry, so a
developer who sees `~/.local/share/rancher-desktop/log_dir/background.log`
has no idea why the fallback fired. Combined with I4, missing-RDD
turns into a silent pile of files in the wrong place.

Fix: `console.warn` the underlying `cause` once when the catch fires,
before returning the Proxy. Capturing the cause in a module-level var
also lets a debug helper surface it in the renderer.

I6. **Production fallback skipped — app dies on missing RDD with no error dialog** — `pkg/rancher-desktop/utils/paths.ts:262-269` [Gemini 3.1 Pro]

```typescript
if (process.env.NODE_ENV !== 'production') {
  const platform = platformOverride ?? process.platform as supportedPlatforms;
  const fallbacks = getPlatformSpecificFallbacks(platform);
  if (fallbacks?.[prop as keyof Paths]) {
    return fallbacks[prop as keyof Paths]?.();
  }
}
throw new Error(`Unable to determine path for ${ String(prop) }: ${ String(cause) }`, { cause });
```

The Proxy gates fallbacks behind `NODE_ENV !== 'production'`. In a
packaged production build with RDD missing or broken, every property
access (starting with `paths.dir` in `background.ts:27`) throws
synchronously before logging is initialized — there is no opportunity
to surface a dialog to the user. Pre-PR behavior was similarly fatal,
but the fallback infrastructure already exists; gating it on
`NODE_ENV` is a deliberate but undocumented choice.

Fix: allow at least one fallback path (e.g., a temp dir) in production
so the main process can boot far enough to display an error dialog,
or document the constraint and add a top-level catch that shows a
friendly diagnostic.

S1. **Replace empty extending interface with type alias** — `pkg/rancher-desktop/utils/paths.ts:49` [Claude Opus 4.7]

```typescript

```

ESLint with `@typescript-eslint/no-empty-object-type` flags this. Use a
type alias instead:

```diff
-export interface Paths extends RDDPaths, RDAPaths { }
+export type Paths = RDDPaths & RDAPaths;
```

S2. **`TEST_PLATFORM` symbol leaks into production module** — `pkg/rancher-desktop/utils/paths.ts:96-98` [Claude Opus 4.7]

```typescript
export const TEST_PLATFORM = Symbol('test-platform');
type supportedPlatforms = 'darwin' | 'linux' | 'win32' | typeof TEST_PLATFORM;
```

A test-only sentinel widens the production type union. The
`getPaths(rddOverride, platformOverride)` signature already accepts a
real platform (`'darwin' | 'linux' | 'win32'`); the "fallback paths if
RDD fails" tests would still pass when parameterized over real
platforms, since the assertions cover the fallback table, not the
platform identity.

S3. **Unused RDD-provided fields** — `pkg/rancher-desktop/utils/paths.ts:16-35` [Claude Opus 4.7]

`args_file`, `docker_socket`, `lima_home`, `pid_file`, `short_dir`,
`tls_dir` round-trip through JSON and `Object.defineProperties` with no
caller in the workspace. Drop the keys until a consumer arrives.

S4. **Reinstate `dockerCliSymlinks` and `limaOverrides` diagnostics under the new path names** — `pkg/rancher-desktop/main/diagnostics/diagnostics.ts:57-60` [Gemini 3.1 Pro]

The PR deletes both diagnostics files outright, presumably because
`paths.lima` and `paths.integration` no longer exist. `paths.lima_home`
is available from `RDDPaths`, and the integration path can be derived
from `~/.rd/bin` (or `paths.dir`). If these checks remain useful to
users, restore them with the new path resolution.

S5. **Trailing semicolon on function declaration** — `pkg/rancher-desktop/utils/paths.ts:136` [Claude Opus 4.7]

```typescript
} satisfies Record<supportedPlatforms, PlatformSpecificPaths>)[platform];
};
```

Function declarations don't take a trailing semicolon; existing style
in the file omits it.

S6. **Test mutates `process.resourcesPath` before snapshotting** — `pkg/rancher-desktop/utils/__tests__/paths.spec.ts:46,107` [Claude Opus 4.7]

## Design Observations

### Concerns

- **Synchronous spawn at module-load time gates app startup** [Claude Opus 4.7] (in-scope). `paths.ts` ends with `export default getPaths()`, which forks `rdd service paths` and blocks until it returns. `background.ts:16` and `logging.ts:230` import `paths` immediately, so every Electron main-process bootstrap pays a synchronous fork+wait. The pre-PR design did the same with `rdctl paths`, so this is not a regression — but the cost is now on the critical path of the daemon-rewrite and worth revisiting. A lazy accessor that memoizes on first read would keep the API the same and defer the cost. No timeout option is passed to `spawnSync` either; a stuck RDD locks the main process until the OS times out.

- **Path semantics conflict between RDD and RDA** [Claude Opus 4.7, Codex GPT 5.5] (in-scope). Inheriting `RDDPaths` and re-exporting it as the application's `Paths` couples the renderer/main code to the daemon's internal naming scheme. RDD's `config` (kubeconfig file) collides with the app's historical `config` (settings dir); RDD's `dir` overlaps with the old `appHome`. An adapter layer that translates the raw RDD JSON into an explicit `AppPaths` type (with disambiguated names like `kubeconfig`, `dataDir`) would prevent C2 and C3 from recurring on every future field rename or addition.

### Strengths

- **Lazy property getters keep test mocks cheap** [Claude Opus 4.7] (in-scope). `platformSpecificPaths` and `platformAgnosticPaths` use getters so values that are not read are not computed. A test only needs to mock the slice it exercises.
- **Splitting `Paths` into `RDDPaths` + `RDAPaths`** [Claude Opus 4.7] (in-scope) makes the source of each field explicit and helps when negotiating the JSON contract with the daemon.
- **Move toward daemon-owned path authority** [Codex GPT 5.5] (in-scope). Routing log and user-data initialization through RDD-derived `dir` / `log_dir` is the right direction for issue #33; it puts startup paths behind the daemon's path authority instead of duplicating platform rules in the app.

## Testing Assessment

The new tests cover the four `spawnSync` failure modes for `getPaths`
and the resolution chain for `getRDDPath` (packaged → relative → PATH
→ throw). Gaps, ranked:

1. **Platform-specific cache and log_dir overrides** — `getPaths` "should
   return all paths" only covers `TEST_PLATFORM`. The darwin/linux
   cache formulae and the darwin `log_dir` override go untested. (See
   S6 / Claude I5.)
2. **Packaged production resource layout** — the new `paths.spec.ts:155-164`
   asserts `paths.resources === undefined` rather than the
   `<resourcesPath>/resources` layout that `electron-builder` packages
   under (C4).
3. **End-to-end coverage of the new path surface** — no test imports
   the full app `Paths` object and exercises remaining consumers
   (snapshots, credential server, deployment profile helpers,
   `commandLineOptions`). C1, C2, and C3 would all surface.
4. **Cache pollution between `getRDDPath` calls** — no test asserts
   that a stale `cachedRDDPath` is or isn't returned to a later
   caller (I3).
5. **Extension protocol regression** — no test verifies
   `x-rd-extension://...` is actually handled after
   `setupProtocolHandlers()` (I1).

E2E test runs against this PR almost certainly fail at compile time
(C1, C2), so no runtime test coverage of the migration is in evidence.

## Design Observations

### Concerns

- **Sync I/O on the renderer-touching module-load path is an architecture regression.** The old `getRdctlPath()` returned `null` quickly when missing; the new design forks RDD synchronously at the top of every Electron renderer/main bootstrap that imports `paths`. Even when RDD is fast, every developer/CI run pays a fork+wait per process. A lazy pattern — `paths` exporting an accessor that only spawns on first read, with results memoized — keeps the API the same but defers the cost. (in-scope; addresses C3)

- **Path semantics conflict between RDD and RDA.** `RDDPaths.config` (kubeconfig file) and `RDDPaths.dir` (app data root) overlap with old RDA names (`config` was the settings dir; `appHome` was the data root). Even after fixing C2, callers reading `paths.config` will reasonably expect a directory. Consider mapping RDD's keys to disambiguated RDA names at the boundary (`kubeconfig`, `dataDir`, etc.), so the on-the-wire JSON shape doesn't dictate the internal API. (future)

### Strengths

- The lazy-getter pattern in `platformSpecificPaths` and `platformAgnosticPaths` is a nice trick for keeping unit-test mocks cheap — values that aren't read aren't computed, so a test only needs to mock the env vars relevant to the slice under test.
- Splitting `Paths` into `RDDPaths` + `RDAPaths` makes the source of each field explicit and will help when negotiating the contract with the daemon.

## Testing Assessment

The test suite covers the new `getRDDPath` resolution chain (packaged → relative → PATH → throw) and the four spawn-failure modes for `getPaths` reasonably well. Missing scenarios, ranked:

This PR migrates the application's path resolution from using the `rdctl paths` command to the Rancher Desktop Daemon (`rdd service paths`). While the internal path fetching and caching logic is improved, removing multiple properties from the `Paths` interface without updating their consumers causes several critical regressions that break snapshots, the credential helper server, e2e tests, and configuration file loading.
