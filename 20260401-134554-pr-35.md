## Important Issues

1. **Patch Content-Type sends JSON Patch header with merge-patch body** — `store/container-engine.ts:122-128` [Gemini 3.1 Pro] (important, regression)

```ts
return client.patchNamespacedContainer(
  {
    name:            container.metadata!.name!,
    namespace:       container.metadata!.namespace!,
    body:            { spec: { state } },
    fieldValidation: 'Strict',
  }).catch((err: Error) => {
```

The generated client's `patchNamespacedContainer` method at `ContainersRancherdesktopIoV1alpha1Api.ts:4673-4679` lists three accepted Content-Types: `application/json-patch+json`, `application/merge-patch+json`, and `application/apply-patch+yaml`. The `getPreferredMediaType` helper at `ObjectSerializer.ts:832-849` selects the first "JSON-like" match — `application/json-patch+json`. That format requires an array of RFC 6902 operations, but the body `{ spec: { state } }` is a merge-patch object. A server that validates Content-Type against body structure will reject every start/stop request.

Fix: Format the body as a JSON Patch array:

```diff
     return client.patchNamespacedContainer(
       {
         name:            container.metadata!.name!,
         namespace:       container.metadata!.namespace!,
-        body:            { spec: { state } },
+        body:            [{ op: 'replace', path: '/spec/state', value: state }],
         fieldValidation: 'Strict',
       }).catch((err: Error) => {
```

Alternatively, if the RDD backend handles merge-patch correctly regardless of Content-Type, add a comment explaining the mismatch so future readers do not "fix" it.

2. **Container grouping reads labels from `metadata` while kube-system filter reads from `status`** — `pages/Containers.vue:218,240-243` [Claude Opus 4.6] (important, regression)

```ts
// Line 218: filter reads status.labels
return this.supportsNamespaces || container.status.labels?.['io.kubernetes.pod.namespace'] !== 'kube-system';

// Lines 240-243: grouping reads metadata.labels
const labels = container.metadata.labels ?? {};
const k8sPodName = labels['io.kubernetes.pod.name'];
```

The kube-system filter at line 218 reads `io.kubernetes.pod.namespace` from `status.labels` (container runtime labels), while the project grouping at lines 240-243 reads the same label keys from `metadata.labels` (Kubernetes resource metadata). If the RDD backend does not copy container runtime labels to `metadata.labels`, grouping never matches on pod name or namespace, and all containers fall into "Standalone Containers." Both code paths were introduced in this PR (confirmed via `git blame`).

Fix: Use the same label source for both operations:

```diff
-            const labels = container.metadata.labels ?? {};
+            const labels = container.status.labels ?? {};
```

3. **Reconnect destroys terminal scrollback** — `components/ContainerLogs.vue:262,98-103,201-203` [Codex GPT 5.4] (important, regression)

```ts
// Line 262: socket 'open' handler
waitingForInitialLogs.value = true;
```

On reconnect, the `open` handler sets `waitingForInitialLogs` to `true` (line 262). Because the template renders the loading indicator and terminal as mutually exclusive `v-if`/`v-else` branches (lines 13-26), this unmounts the terminal `<div>`. Unmounting triggers the `watch(terminalContainer)` cleanup (lines 98-103), which aborts the `terminalAborter` and disposes the `Terminal` instance (lines 138-140). Additionally, the stream cleanup at lines 201-203 calls `terminal?.reset()` and clears the buffer. The comment at lines 259-261 says the user should keep seeing old logs during a disconnect, but the implementation destroys them.

Fix: Keep the terminal mounted during reconnects. Use `visibility: hidden` or an overlay for the loading state instead of `v-if`/`v-else`, so the terminal DOM element persists across reconnection cycles. Only create a new Terminal when the container identity changes.

## Suggestions

1. **`portsSortKey` uses lexicographic sort on numbers** — `pages/Containers.vue:302` [Claude Opus 4.6] (suggestion, regression)

```ts
portsSortKey: portList.map(([hostPort]) => hostPort).sort(),
```

JavaScript's `Array.prototype.sort()` without a comparator converts elements to strings. `[80, 443, 3000].sort()` produces `[3000, 443, 80]`. Since `SortableTable` compares array elements to determine row order, the wrong element order within the key produces incorrect column sorting.

Fix:

```diff
-portsSortKey: portList.map(([hostPort]) => hostPort).sort(),
+portsSortKey: portList.map(([hostPort]) => hostPort).sort((a, b) => a - b),
```

2. **Stopped containers never begin streaming after they start** — `components/ContainerLogs.vue:191,312-318` [Codex GPT 5.4] (suggestion, gap)

```ts
// Line 191: watcher dependencies
watch([logURL, reconnectTrigger], async([logURL], _, cleanUp) => {

// Lines 312-317: suppresses retry for stopped containers
function handleStreamError() {
  clearTimeout(reconnectTimer);
  if (!isRunning) {
    return;
  }
```

The log-stream watcher at line 191 depends only on `logURL` and `reconnectTrigger`. If the user opens logs for a stopped container, the WebSocket fails and `handleStreamError` (line 314) suppresses the retry because `isRunning` is `false`. When that container later starts, neither `logURL` (based on container name, not state) nor `reconnectTrigger` changes, so the watcher never fires. The user must navigate away and back to see logs.

Fix: Add `isRunning` (or the container's status) as a watch dependency and trigger a reconnect when it transitions to `running`.

Most of the prior review feedback has been addressed, but a critical regression was introduced in how the Kubernetes API patch payload is formatted, which will cause API servers to reject state transition requests.

### Findings

#### Critical Issues

1. **JSON Patch request uses Merge Patch payload format** — `pkg/rancher-desktop/store/container-engine.ts:115-119`

```typescript
    return client.patchNamespacedContainer(
      {
        name:            container.metadata!.name!,
        namespace:       container.metadata!.namespace!,
        body:            { spec: { state } },
        fieldValidation: 'Strict',
      }).catch((err: Error) => {
```

The generated Kubernetes API client `patchNamespacedContainer` method defaults its `Content-Type` header to `application/json-patch+json`. However, the `body` is provided as a merge-patch object (`{ spec: { state } }`). Because the API server strictly validates `application/json-patch+json` payloads against the JSON Patch standard (which requires an array of patch operations), this request will fail with an HTTP 400 Bad Request.

**Fix**: Provide a valid JSON Patch array instead. Using `add` is safer in case the `/spec` base is partially initialized.

```diff
     return client.patchNamespacedContainer(
       {
         name:            container.metadata!.name!,
         namespace:       container.metadata!.namespace!,
-        body:            { spec: { state } },
+        body:            [{ op: 'add', path: '/spec/state', value: state }],
         fieldValidation: 'Strict',
       }).catch((err: Error) => {
```

#### Important Issues

2. **Table sort relies on potentially undefined `status.name`** — `pkg/rancher-desktop/pages/Containers.vue:183`

```typescript
        {
          name:  'containerName',
          label: this.t('containers.manage.table.header.containerName'),
          sort:  ['status.name', 'imageName'],
        },
```

The `sort` arrays across almost all table columns (e.g., `containerName`, `imageName`, `ports`, `uptime`) rely on `status.name` as a primary or secondary sort key. However, `container.status.name` can be undefined (which is why the template gracefully falls back to `metadata.name` via `row.status?.name || row.metadata?.name`). If `status.name` is missing, `@rancher/components`'s `SortableTable` receives `undefined` for that key, silently breaking or corrupting the sort order. It does not automatically fall back to `metadata.name`.

**Fix**: Add a normalized `containerName` property to the mapped `RowItem` array and use it in all `sort` definitions instead of `status.name`.

### Design Observations

#### Strengths

- **Vuex Getter Type Safety:** The use of TS 4.1 Key Remapping and `Intersect<Values<...>>` in `pkg/rancher-desktop/typings/store.d.ts` is an exceptionally robust way to type Vuex's flattened getters map. It elegantly ignores Vuex modules that do not define getters by inherently omitting `never` from the union, resulting in incredibly solid type safety without hardcoding modules.
- **ResizeObserver Cleanup:** The lifecycle hook inside the `watch` closure in `ContainerLogs.vue` correctly cleans up the `ResizeObserver` associated with the template ref. This properly handles DOM detachment across re-renders without memory leaks.

### Testing Assessment

1. **API Client Payloads**: There is a high risk of regression when interacting with the generated OpenAPI client endpoints, specifically regarding `Content-Type` expectations. Consider adding unit tests that mock the `config.makeApiClient` return value and verify the exact payloads (and operations) passed to `patchNamespacedContainer`.
