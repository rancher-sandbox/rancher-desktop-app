## Executive Summary

This PR migrates the Images page from the legacy IPC-based image manager to the RDD (Rancher Desktop Daemon) Kubernetes-style API, following the pattern established by the Volumes and Namespaces conversions. It adds image resource definitions and watch infrastructure to the `container-engine` store, reworks image parsing and display in the component, and wires delete/push actions through the generated RDD client. The PR description acknowledges that "lots of things are expected to be broken" and that image pulling does not yet work.

The review found one clear bug (stale sort column reference), several error-handling gaps, and a handful of dead-code and consistency issues.

## Critical Issues

1. **Stale `default-sort-by` references a renamed column** — `pkg/rancher-desktop/components/Images.vue:15` [Claude Opus 4.6, Codex GPT 5.4] (critical, regression)

```html
<SortableTable
  ...
  default-sort-by="imageName"
  :headers="headers"
```

The header column was renamed from `imageName` to `name` (line 218), but `default-sort-by` still references `"imageName"`. The SortableTable sorting logic looks for a header whose `name` matches `sortBy`; no header is named `"imageName"`, so the sort falls through to a default of `['nameSort', 'id']`. Because these rows lack a `nameSort` property, the table sorts by `id` on initial load instead of by image name.

Fix:
```diff
- default-sort-by="imageName"
+ default-sort-by="name"
```

2. **`imagePush` errors silently dropped** — `pkg/rancher-desktop/store/container-engine.ts:83-104`, `pkg/rancher-desktop/components/Images.vue:431-433` [Claude Opus 4.6, Gemini 3.1 Pro] (important, regression)

```typescript
// store/container-engine.ts
imagePush(
  { rootState },
  { image }: { ... },
) {
  const config: RDDClient.KubeConfig = rootState['rdd-connection'].config;
  const client = config.makeApiClient(RDDClient.ContainersRancherdesktopIoV1alpha1Api);
  return client.createNamespacedImagePushRequest({...});
},

// components/Images.vue
doPush(image: ParsedImage) {
  // TODO: This should display push output.
  this.imagePush({ image });

```

Unlike `imageDelete` (line 127), which wraps the API call in try/catch and commits errors via `SET_ERROR`, `imagePush` returns the raw promise with no error handling. The component's `doPush` does not `await` the result either. A failed push produces an unhandled promise rejection with no user feedback. The same gap exists in `imageScan` (line 105), though that action is currently unused.

Fix: Add error handling to `imagePush` matching the `imageDelete` pattern:
```diff
- imagePush(
-   { rootState },
+ async imagePush(
+   { rootState, commit },
    { image }: { ... },
  ) {
    const config: RDDClient.KubeConfig = rootState['rdd-connection'].config;
    const client = config.makeApiClient(...);
-   return client.createNamespacedImagePushRequest({...});
+   try {
+     await client.createNamespacedImagePushRequest({...});
+   } catch (error: any) {
+     commit('SET_ERROR', { error, source: 'images' });
+   }
  },
```

And await it in the component:
```diff
- doPush(image: ParsedImage) {
+ async doPush(image: ParsedImage) {
    // TODO: This should display push output.
-   this.imagePush({ image });
+   await this.imagePush({ image });
  },
```

3. **`scanImage` uses `??` instead of `||` for empty-string fallback** — `pkg/rancher-desktop/components/Images.vue:438` [Gemini 3.1 Pro] (important, regression)

```typescript
scanImage(row: ParsedImage) {
  this.$router.push({
    name:   'images-scans-image-name',
    params: { image: row.reference ?? row.id, namespace: this.selectedNamespace },
  });
},
```

`ParsedImage.reference` is derived from `image.status.repoTag ?? ''` (line 261). For untagged images, `reference` is `""` (empty string). The nullish coalescing operator `??` does not trigger on empty strings — only on `null` or `undefined` — so the fallback to `row.id` never fires. The route receives an empty `image` parameter.

Fix:
```diff
- params: { image: row.reference ?? row.id, namespace: this.selectedNamespace },
+ params: { image: row.reference || row.id, namespace: this.selectedNamespace },
```

4. **Protected image matching may break with registry-prefixed references** — `pkg/rancher-desktop/pages/Images.vue:52-56`, `pkg/rancher-desktop/components/Images.vue:441-442` [Gemini 3.1 Pro] (important, regression)

```typescript
// pages/Images.vue — rancherImages computed
return (this.images ?? [])
  .map(image => image.status?.repoTag)
  .filter(defined)
  .map(reference => reference.replace(/:.*?$/, ''))
  .filter(name => name.startsWith('rancher/'));

// components/Images.vue — isDeletable
isDeletable(row: ParsedImage) {
  return !this.protectedImages.includes(row.name);
},
```

Before this PR, `isDeletable` checked `row.imageName`, which was a short name (e.g., `moby/buildkit`). This PR switches to `row.name`, which is parsed from `repoTag` and may include a registry prefix (e.g., `docker.io/moby/buildkit`). Similarly, `rancherImages` uses `.startsWith('rancher/')`, which fails if `repoTag` includes a registry prefix like `docker.io/rancher/k3s`. The `protectedImages` list includes the literal `'moby/buildkit'` (line 65), which would not match `'docker.io/moby/buildkit'`.

Whether this actually triggers depends on the reference format the RDD API returns. If Docker Hub images come back without the `docker.io/` prefix, the matching works. If they include the prefix, protected images become deletable.

Fix: Use the parsed `repository` field (which strips the registry) for comparison, or normalize the protected image list:
```diff
  isDeletable(row: ParsedImage) {
-   return !this.protectedImages.includes(row.name);
+   return !this.protectedImages.some(p => p === row.name || p === row.repository);
  },
```

## Design Observations

### Concerns

- **(in-scope)** The output window infrastructure (`ImagesOutputWindow`, `startImageManagerOutput`, `startRunningCommand`, `imageOutputCuller`, `Card`) remains in the component but is now unreachable: `showImageManagerOutput` returns `keepImageManagerOutputWindowOpen`, which is `false` and never set to `true` because `startImageManagerOutput()` is never called. The TODO comments acknowledge that deletion/push output display is not yet implemented. Once output display is wired through the RDD API, this infrastructure may not be the right shape. [Claude Opus 4.6]

- **(in-scope)** The page splits UI preference responsibility: RDD-backed resource state lives in `container-engine`, while image-page preferences (`showAll`, `namespace`) were removed from the old Electron settings IPC but not replaced. The `settings` data property is pinned to `defaultSettings` and never updated. Consolidating `currentNamespace` and `showAll` into one store-backed source of truth would remove the mismatch. [Codex GPT 5.4]

- **(future)** Namespace switching does not restart the image watcher. `watchImages` runs once on mount (line 97); `onChangeNamespace` only commits `currentNamespace` via `setCurrentNamespace`. The `listContainerNamespacedResource` function applies `fieldSelector` during the initial list (line 20) but the watch stream does not carry the selector. Once `supportsNamespaces` is enabled, selecting a namespace will not reliably filter images. [Codex GPT 5.4]

### Strengths

- The image reference parsing in `parsedImages` (lines 250-278) is well-documented with ASCII art and handles edge cases (untagged images, registries with ports) cleanly. [Claude Opus 4.6]
- Moving image mutations into the `container-engine` store aligns images with the existing RDD resource/watch pattern used for volumes, keeping API calls out of the view layer. [Claude Opus 4.6, Codex GPT 5.4]

## Testing Assessment

No tests are added or modified. Given the PR description acknowledges this is WIP, the absence is understandable, but the following scenarios carry the most risk:

1. **Image reference parsing** — the regex in `parsedImages` handles registries with ports, multiple path segments, and untagged images. Unit tests would prevent regressions as the RDD API's reference format stabilizes.
2. **`setCurrentNamespace` validation** — the action throws on nonexistent namespaces; a unit test for the happy path and the error path would be straightforward.
3. **Empty image list** — no test covers the zero-images state, so the missing `ImagesButtonAdd` action went undetected.
4. **`imageDelete` error handling** — the success/failure branching in the store action is testable in isolation.
