## Executive Summary

Round 3 is a force-pushed rebase of round 2 onto current main; `pkg/rancher-desktop/store/rddConnection.ts` and `pkg/rdd-client/watch.ts` are byte-identical between the two HEADs (rebase pickup of a `settled`/`created`/`running` getter rename in `rdd.ts` and a `containerSetState` → `containerRequestAction` rename in `container-engine.ts` from main are the only PR-irrelevant changes). None of round 2's three Important findings or ten Suggestions were addressed.

The most consequential new finding this round is I1 (`Watcher.close()` clears the `#notifyDelay` timer but leaves the field at its now-cancelled timer-id, so `onChange()`'s "already-scheduled" guard silently blocks every subsequent state commit on the post-`start()` watcher). Round 2 missed this; the rewatch redesign that added `Watcher` instance reuse made the bug reachable. Round 2's I2 (`clearTimeout` runs before the stale-watcher check in the `error` handler, so a deferred error from a closed `ListWatch` cancels a still-pending 429 restart on the live watcher) is also still present at the same lines.

The agent panel disagreed sharply on the `fetchConfig` memoization: Codex labelled it Important and Gemini Critical, both arguing that a daemon credential rotation would leave watchers unrecoverable. The consolidator demotes to Suggestion (S3). The renderer-side memoization is real, but `pkg/rancher-desktop/main/rdd-ctl.ts:23-27` shows the main-process IPC handler also caches `lastKubeConfig` permanently — so even pre-PR `doneFn`'s "invalidate config and refetch" was theatrical (the IPC would have returned the cached config anyway). The PR drops the theatre but does not change observable runtime behaviour; what's left is a stale comment (`// The old config is no longer valid` at line 434) misleading future readers, and a missing diagnostic surface for kube-config fetch failures (S4).

Author has signalled "too many rounds of local AI review; at this point it's just kind of nit-picking" on PR #47. I1 and I2 are concrete races, not nits. Everything else in this report is calibrated to that signal.

## Important Issues

I1. **`Watcher.close()` leaves a stale timer-id in `#notifyDelay`, silently blocking every post-rewatch state commit** — `pkg/rancher-desktop/store/rddConnection.ts:691,703-709` [Claude Opus 4.7]

```ts
protected onChange() {
  if (this.#notifyDelay) {
    return;
  }
  this.#notifyDelay = setTimeout(() => {
    const key = `SET_${ UpperSnakeCase(this.#type) }` as `SET_${ UpperSnakeCase<K> }`;
    this.#notifyDelay = undefined;
    this.#items = this.#watcher?.list(this.#namespace) ?? [];
    this.#commit(key, this.#items);
    this.#loaded.resolve();
  }, 0);
}

close() {
  clearTimeout(this.#notifyDelay);
  clearTimeout(this.#restartTimeout);
  this.#loaded.reset();
  this.#loaded.catch(() => { /* ignore */ });
  return this.#watcher?.stop(errorManuallyStopped);
}
```

`onChange()` uses `this.#notifyDelay` as an "already-scheduled" guard — non-undefined means a coalesce window is open. Only the deferred callback at line 696 clears it back to `undefined`. `close()` cancels the pending callback with `clearTimeout`, but `clearTimeout` does not nullify the variable; the cancelled `Timeout` object remains, and remains truthy.

After `rewatchResources` runs `watcher.close()` followed by `watcher.start()` (lines 547-549), the post-start `ListWatch` fires its first `change` event, the handler calls `this.onChange()`, the guard at line 691 sees the stale timer-id, and the early return prevents any further commit. The new watcher is alive on the wire — its `change` events keep firing — but the renderer never updates. Pages stay parked on pre-rewatch data until the user navigates away and back.

The bug fires only when `close()` runs while a `setTimeout` callback is in flight (the window between `onChange()` scheduling the 0ms timer and the timer firing). For event-driven `rewatchResources` triggered synchronously from the `rdd-connection` namespace-change watcher, container-engine watchers actively receiving events at the moment of namespace change are inside that window. Pre-`fcbf5657e` the Watcher was reconstructed on every reconnect, so the field was a fresh `undefined`; the new design reuses the instance and exposes the stale-id.

Fix: reset both timer fields in `close()`.

```diff
   close() {
     clearTimeout(this.#notifyDelay);
+    this.#notifyDelay = undefined;
     clearTimeout(this.#restartTimeout);
+    this.#restartTimeout = undefined;
     this.#loaded.reset();
     this.#loaded.catch(() => { /* ignore */ });
     return this.#watcher?.stop(errorManuallyStopped);
   }
```

Resetting `#restartTimeout` is defence-in-depth — the field is not currently used as a truthy guard, but I2 below shows the same field interacts with state checks, so symmetric handling closes a class of bug rather than a single instance.

(important, regression)

I2. **`clearTimeout` runs before the stale-watcher check; a stale `error` event cancels a live 429 restart** — `pkg/rancher-desktop/store/rddConnection.ts:640-668` [Claude Opus 4.7]

```ts

  clearTimeout(this.#restartTimeout);
  if (!Object.is(watcher, this.#watcher)) {
    // This error is from a stale watcher; ignore it.
    return;
  }
  this.#loaded.reset();
  this.#loaded.catch(() => { /* ignore */ });
  if (Object.is(err, errorManuallyStopped)) {
    return;
  } else if (err.statusCode === 429) {
    ...
    this.#restartTimeout = setTimeout(() => this.start(), delay * 1_000);
    return;
  }
  ...
});
```

This is round 2's I2 unaddressed. The `change`, `connect`, and `start().catch` handlers (lines 628-639, 671-679) all run the `Object.is(watcher, this.#watcher)` stale-check before touching any per-`Watcher` field; the `error` handler is the lone outlier and clears state up front.

Concrete sequence:

1. Inner `ListWatch` A is running.
2. A is closed by `start()`'s line 618 (`this.#watcher?.stop(errorManuallyStopped)`) on a namespace change; the abort propagates asynchronously.
3. Line 627 assigns `this.#watcher = B`.
4. B's `start()` runs, hits a 429, sets `this.#restartTimeout = setTimeout(() => this.start(), delay)`.
5. A's `'error'` event finally fires (with `errorManuallyStopped` as the reason).
6. The handler executes `clearTimeout(this.#restartTimeout)` — clearing **B's** restart — then `!Object.is(A, B)` is true and returns.
7. B's restart never fires; the watcher is silently parked. No further `error`, `change`, or `connect` event will trigger it back to life until the next external `rewatchResources`.

Round 2 documented this with the same trace; round 3 ships the same bytes at lines 640-642. Confirmed via `git show fcbf5657e:pkg/rancher-desktop/store/rddConnection.ts | sed -n '640,650p'` matching round 2 verbatim.

Fix: move the `clearTimeout` after the stale-check, mirroring the other handlers.

```diff

-  clearTimeout(this.#restartTimeout);
   if (!Object.is(watcher, this.#watcher)) {
     // This error is from a stale watcher; ignore it.
     return;
   }
+  clearTimeout(this.#restartTimeout);
+  this.#restartTimeout = undefined;
```

## Design Observations

### Strengths

- *(in-scope)* The `Object.is(watcher, this.#watcher)` staleness check in every `ListWatch` event handler (`change`, `connect`, `error`, `start().catch`) is the right pattern for letting the same `Watcher` instance survive a `ListWatch` swap. It centralises the "is this the live watcher" decision in one form across handlers and avoids the alternative of unhooking listeners. (The `error` handler's clear-before-check is I2, not a refutation of the pattern.) [Claude Opus 4.7]
- *(in-scope)* Per-resource reconnect (the `doReconnect` closure in `setupResourceWatch`'s `doneFn`) replaces the pre-PR global `notifyDisconnected` fan-out and removes a real race the commit message calls out. [Claude Opus 4.7]
- *(in-scope)* `defineResource` ergonomics: clients with auto-detected `listNamespaced<Type>` no longer need an explicit `list` field, meaningfully reducing boilerplate at the resource definitions in `container-engine.ts` and `rdd.ts`. [Claude Opus 4.7]
- *(in-scope)* Tracking namespaced resources in `rdd-connection.namespacedResources` (a `Record<string, Set<string>>`) and dispatching `rewatchResources` per module on namespace change is cleaner than the prior disconnect-callback indirection. [Codex GPT 5.5]
- *(in-scope)* The `Latch.settled` accessor is a minimal addition wired into `resolve`/`reject`/`reset`. The `setupResourceWatch` "called more than once" guard that uses it has the right shape (S8 documents a dormant edge). [Gemini 3.1 Pro]

### Concerns

- *(future)* **Two-stage namespace propagation has three concurrent triggers and no serialisation** — `setupResourceWatch` at startup, the `rdd-connection` namespace-change watcher, and the per-resource `doneFn` reconnect path all mutate watcher state through `close()` / `start()` (or `setTimeout(doReconnect)`). As more modules add namespaced resources the rewatch loop becomes the choke point. Consider serialising the rewatch loop (one in-flight rewatch at a time per module), or making the namespace state a single source-of-truth with an explicit version that watchers reconcile against. Out of scope for this PR but worth tracking. [Claude Opus 4.7]

- *(future)* **Startup window where `rdd-connection.namespace = 'default'` triggers wrong-namespace list calls** — until the apps watcher delivers an App with the correct `spec.namespace`, every container-engine watcher started by `watchResources` lists from `/apis/.../namespaces/default/...`. On a fresh install where the App does not yet exist, this returns 404 / empty, then `rewatchResources` redoes the list once `ensureAppStarted` creates the App. Self-healing, but the user can briefly see no data on the Containers page during cold start. Either gate the container-engine `setupResourceWatch` behind `kubernetesNamespace !== undefined`, or seed `rdd-connection.namespace` from a more reliable source. [Claude Opus 4.7]

## Review Process Notes

### Skill improvements

- **Treat `clearTimeout(field)` followed by `(if !valid) return` as a race smell, regardless of which event is firing.** When a handler reads or mutates per-instance timer state before checking whether it owns the instance (for example, before a stale-watcher `Object.is` check), flag it. The pattern is symmetric across the four `ListWatch` event handlers and the lone outlier is a strong signal — review every event handler in a class side-by-side and confirm the staleness check runs first uniformly. Why: this kind of race produces silent permanent failure (no error, no log, no recovery path), so it is invisible at runtime and survives review unless the reviewer enumerates every handler.

- **Treat `clearTimeout(field)` without `field = undefined` as a stale-id smell when the same `field` is used as a truthy "already-scheduled" guard.** `clearTimeout` cancels the pending callback but does not nullify the variable; the cancelled `Timeout` object remains truthy. Any subsequent code that uses `if (this.#field)` as a guard will see the stale id and skip its work. Search for the pattern by grepping for `clearTimeout(this.#` and checking whether the same field appears in a truthy-guard `if`. The fix is always a one-line `field = undefined` after the clear.

### Repo context updates

- **[repo] [ADD] `lastKubeConfig` in `pkg/rancher-desktop/main/rdd-ctl.ts:15-27` is a one-shot module-level cache of the kubeconfig.** When reviewing renderer-side caching of the kube-config (in `rdd-connection.ts` or any consumer), trace through to the main-process side before calling a regression. The IPC handler at line 61 short-circuits via `if (lastKubeConfig)`, so renderer-side "invalidate and refetch" patterns return the same value the IPC originally produced. A real cache-invalidation path requires changes at both layers. Add this to repo context so future deep reviews don't double-flag fetchConfig memoization as a critical/important regression when the layer below already has the same property.

**I1. `Watcher.close()` leaves a stale timer ID in `#notifyDelay`, silently disabling future state commits after a rewatch** — `pkg/rancher-desktop/store/rddConnection.ts:691-709` (important, regression)

```typescript

    return;
  }
  this.#notifyDelay = setTimeout(() => {
    ...
    this.#notifyDelay = undefined;
    this.#items = this.#watcher?.list(this.#namespace) ?? [];
    this.#commit(key, this.#items);

  clearTimeout(this.#notifyDelay);
  clearTimeout(this.#restartTimeout);
  this.#loaded.reset();
```

`onChange()` at line 691 uses `this.#notifyDelay` as a "notify already pending" guard, and only the deferred callback (line 696) clears it back to `undefined`. `close()` at line 704 calls `clearTimeout(this.#notifyDelay)`, which cancels the deferred callback, but does **not** reset the field — `setTimeout` returns a truthy timer id/object that lingers. ```diff

```diff
+    this.#notifyDelay = undefined;

+    this.#restartTimeout = undefined;
     this.#loaded.reset();
```

## Design Observations

### Concerns

- **Two-stage namespace propagation has three concurrent triggers and no serialisation** *(future)* — `setupResourceWatch` at startup, the `rdd-connection` namespace-change watcher, the `setCurrentNamespace` action in `container-engine.ts`, and the per-resource doneFn reconnect path all mutate watcher state through `close()` / `start()` (or `setTimeout(doReconnect)`).
