## Executive Summary

This round 2 review covers the same PR after the author addressed four findings from round 1: fetchConfig race deduplication (I1), containerSetState Content-Type (I6), disconnect callback key collision (I8), and setCurrentNamespace callback replacement (S9). The core architecture — refcounted `watchResources`/`unwatchResources` with centralized `setupResourceWatch` — remains solid.

Two agents independently confirmed that the `doneHandler` ordering bug dismissed in round 1 (I7) is real: when a component unmounts and closes its watcher, the abort error fires ERROR callbacks before the `stopped` flag is checked, triggering a full backend reconnect on every page navigation. This is the only finding that blocks merge. One new finding surfaced: the `Watcher.#loaded` latch is not reset when a stopped watcher restarts, so `waitForResources` rejects permanently after a stop/start cycle.

## Important Issues

I1. **Intentional watcher close triggers spurious global reconnect** — `pkg/rdd-client/cache.ts:165-176` [Codex GPT 5.4, Gemini 3.1 Pro]

```typescript
private async doneHandler(err: any): Promise<void> {
    this._stop();
    if (
      err &&
      ((err as { statusCode?: number }).statusCode === 410 || (err as { code?: number }).code === 410)
    ) {
      this.resourceVersion = '';
    } else if (err) {
      this.callbackCache[ERROR].forEach((elt: ErrorCallback) => elt(err));
      return;
    }
    if (this.stopped) {
      // do not auto-restart
      return;
    }
```

When a component unmounts and `unwatchResources` reduces the refcount to zero, `Watcher.close()` calls `ListWatch.stop()`, which sets `this.stopped = true` and aborts the request. The abort produces an `AbortError` in `watch.ts:110-117` that flows to `doneHandler`. Because the `else if (err)` branch at line 172 fires ERROR callbacks *before* the `this.stopped` check at line 176, every intentional close triggers the full disconnect path: `notifyDisconnected`, config clear, and reconnect scheduling. Ordinary page navigation causes a backend reconnect storm.

The author dismissed round 1's I7 finding, stating the error handler "is only for HTTP status 410." Tracing through `watch.ts` confirms this is incorrect: `controller.signal.aborted` is true (so the `else` branch calls `doneCallOnce(err)` with the `AbortError`), and `AbortError` is not a 410, so it hits the `else if (err)` branch.

Fix: Move the `stopped` check above the error processing.

```diff
 private async doneHandler(err: any): Promise<void> {
   this._stop();
+  if (this.stopped) {
+    return;
+  }
   if (
     err &&
     ((err as { statusCode?: number }).statusCode === 410 || (err as { code?: number }).code === 410)
   ) {
     this.resourceVersion = '';
   } else if (err) {
     this.callbackCache[ERROR].forEach((elt: ErrorCallback) => elt(err));
     return;
   }
-  if (this.stopped) {
-    // do not auto-restart
-    return;
-  }
```

I2. **Restarting a stopped watcher does not reset the `loaded` latch** — `pkg/rancher-desktop/store/rddConnection.ts:610-616` [Codex GPT 5.4]

```typescript
start() {
    this.#watcher.start().catch(err => {
      console.debug(`Watch ${ this.#type } ended:`, err);
      this.#doneFn(err);
      this.#loaded.reject(err);
    });
}
```

`Watcher.#loaded` is a `Latch` (a Promise with exposed `resolve`/`reject` methods) created once at construction (line 552). When the watcher encounters an error, the error handler at line 605 calls `this.#loaded.reject(err)`. A settled Promise ignores subsequent `resolve` calls, so restarting the watcher via `watchResources` (which calls `start()` at line 494) leaves `#loaded` permanently rejected. Any subsequent `waitForResources` call rejects immediately, even though the watcher is running and receiving data.

This bug compounds with I1: intentional closes via `unwatchResources` reject `#loaded` through the spurious error path. With the I1 fix applied, intentional closes no longer reject `#loaded`, but genuine backend errors still do — and the latch remains stale until `setupResourceWatch` recreates the Watcher.

Fix: Reset the latch in `start()`.

```diff
 start() {
+  this.#loaded = Latch();
+  this.#loaded.catch(() => { /* ignore */ });
   this.#watcher.start().catch(err => {
     console.debug(`Watch ${ this.#type } ended:`, err);
     this.#doneFn(err);
     this.#loaded.reject(err);
   });
 }
```

## Design Observations

**Concerns**

1. **(in-scope)** The watch lifecycle has no semantic distinction between intentional close and backend disconnect. `ListWatch.stop()` and a backend-initiated disconnect both flow through the same error path, producing the cascade behind I1. Introducing an `intentionallyClosed` flag in `ListWatch` or splitting `doneHandler` into separate paths would eliminate this class of bugs. [Codex GPT 5.4, Gemini 3.1 Pro]

2. **(in-scope)** View lifecycles directly drive transport teardown. A component unmounting closes the underlying HTTP connection. Keeping informers alive for the process lifetime and using refcounts only to gate store commits would remove the need to reinterpret aborts as disconnects. [Codex GPT 5.4]

**Strengths**

1. The refcounted `watchResources`/`unwatchResources` API handles overlapping component lifecycles cleanly. When two components watch the same resource, the watcher runs as long as either is active. [All agents]

2. The `fetchConfig` deduplication via `fetchConfigPromise` (new in this round) prevents concurrent reconnection storms without adding complexity. [Claude Opus 4.6]

3. Lazy `fieldSelector`/`labelSelector` evaluation via functions ensures namespace changes propagate to watchers on reconnect without rebuilding them. [Claude Opus 4.6]

4. The `setHeaderOptions` middleware approach for overriding Content-Type avoids modifying generated code and composes well with other middleware. [Claude Opus 4.6]

## Design Observations

**Strengths**

- The refcounting mechanism is well-designed: the `_watchersInitialized` latch gates access until setup completes, the refcount correctly manages start/stop of underlying watchers, and the `setupResourceWatch` preserves refcounts across reconnections so watchers auto-restart without components re-subscribing.

- Converting `fieldSelector`/`labelSelector` to functions (evaluated lazily in `cache.ts` lines 201-206 and passed as closures from rddConnection.ts lines 441-442) ensures that namespace changes are picked up on reconnect without rebuilding the watcher — an elegant solution to the stale-selector problem.

- The `fetchConfig` deduplication via `fetchConfigPromise` (rddConnection.ts lines 58-88) prevents concurrent reconnection storms without adding complexity.

- The two-phase app startup (create with `running: false`, then patch to `running: true`) cleanly separates the "ensure exists" concern from the "start" concern, handling the TOCTTOU race via 409 detection.
