Executive Summary ¶

This PR replaces rdctl paths with rdd service paths and reshapes the Paths interface around RDD-provided keys (dir, log_dir, cache, config, …). The migration is substantially incomplete: several production and test files still reference the old Paths properties (appHome, deploymentProfileUser, getRdctlPath), one property name silently changes meaning (config: settings dir → kubeconfig file), and the new paths.resources getter no longer appends the resources/ subdirectory that electron-builder packages assets under, breaking icon, preload, and tray-icon resolution in packaged builds. Several unmigrated callers will fail TypeScript compilation; the rest will break at runtime. Structure (Critical 4, Important 6, Suggestions 6).

Design Observations ¶

Concerns ¶

  • Synchronous spawn at module-load time gates app startup Claude (in-scope). paths.ts ends with export default getPaths(), which forks rdd service paths and blocks until it returns. background.ts:16 and logging.ts:230 import paths immediately, so every Electron main-process bootstrap pays a synchronous fork+wait. The pre-PR design did the same with rdctl paths, so this is not a regression — but the cost is now on the critical path of the daemon-rewrite and worth revisiting. A lazy accessor that memoizes on first read would keep the API the same and defer the cost. No timeout option is passed to spawnSync either; a stuck RDD locks the main process until the OS times out.
  • Path semantics conflict between RDD and RDA Claude Codex (in-scope). Inheriting RDDPaths and re-exporting it as the application's Paths couples the renderer/main code to the daemon's internal naming scheme. RDD's config (kubeconfig file) collides with the app's historical config (settings dir); RDD's dir overlaps with the old appHome. An adapter layer that translates the raw RDD JSON into an explicit AppPaths type (with disambiguated names like kubeconfig, dataDir) would prevent C2 and C3 from recurring on every future field rename or addition.

Strengths ¶

  • Lazy property getters keep test mocks cheap Claude (in-scope). platformSpecificPaths and platformAgnosticPaths use getters so values that are not read are not computed. A test only needs to mock the slice it exercises.
  • Splitting Paths into RDDPaths + RDAPaths Claude (in-scope) makes the source of each field explicit and helps when negotiating the JSON contract with the daemon.
  • Move toward daemon-owned path authority Codex (in-scope). Routing log and user-data initialization through RDD-derived dir / log_dir is the right direction for issue #33; it puts startup paths behind the daemon's path authority instead of duplicating platform rules in the app.

Testing Assessment ¶

The new tests cover the four spawnSync failure modes for getPaths and the resolution chain for getRDDPath (packaged → relative → PATH → throw). Gaps, ranked:

  1. Platform-specific cache and log_dir overrides — getPaths "should return all paths" only covers TEST_PLATFORM. The darwin/linux cache formulae and the darwin log_dir override go untested. (See S6 / Claude I5.)
  2. Packaged production resource layout — the new paths.spec.ts:155-164 asserts paths.resources === undefined rather than the <resourcesPath>/resources layout that electron-builder packages under (C4).
  3. End-to-end coverage of the new path surface — no test imports the full app Paths object and exercises remaining consumers (snapshots, credential server, deployment profile helpers, commandLineOptions). C1, C2, and C3 would all surface.
  4. Cache pollution between getRDDPath calls — no test asserts that a stale cachedRDDPath is or isn't returned to a later caller (I3).
  5. Extension protocol regression — no test verifies x-rd-extension://... is actually handled after setupProtocolHandlers() (I1).

E2E test runs against this PR almost certainly fail at compile time (C1, C2), so no runtime test coverage of the migration is in evidence.

Documentation Assessment ¶

  • The RDDPaths interface comments are precise and well-formatted.
  • getPaths JSDoc (lines 207-213) documents rddOverride and the throw, but not platformOverride or the silent Proxy-fallback on RDD failure. Add a @returns line noting the Proxy semantics.
  • The note @note These are not used in production. (line 155) is inaccurate: dev callers that hit the fallback Proxy do use these paths, and (per I6) a misconfigured production install can hit them too.
  • No CHANGELOG entry captures the migration of ~/.local/share/rancher-desktop/logs to whatever RDD now reports. This path is user-visible.
