## Executive Summary

This PR wires three new container actions (pause / unpause / restart) into the Containers UI by extending the existing `containerRequestAction` patch flow, plus two drive-by fixes: a missing `Banner` import in `ContainerInfo.vue` and `AbortError` suppression in the watcher's error handler. The mechanical wiring is correct and reuses the established annotation-action pattern.

The headline concern, which all three reviewers raised independently, is that none of the new action callers (nor the existing start/stop/delete callers they mirror) watches `status.lastAction` to surface daemon-side failures. Because the patch promise only confirms the daemon *recorded* the request, a failed pause/unpause/restart resolves cleanly with no banner and no log line. The repo's review context is explicit that any new annotation-action caller must either surface `status.lastAction` failures or document why no UI feedback is needed; this PR does neither.

Secondary concerns: the new `AbortError` branch is broad defense-in-depth that silently bypasses the reconnect path; `Restart` is disabled for stopped containers and `Stop` for paused containers (a UX edge worth confirming against the daemon's transition rules); pause/unpause/restart labels are hard-coded English while `Delete` is i18n'd via a stale `images.*` key.

Structure: 3 commits, each one concept; 3 files (+60/−13).

## Important Issues

I1. **New container actions never surface asynchronous backend failures** — `pkg/rancher-desktop/pages/Containers.vue:316-333` [Claude Opus 4.7] [Codex GPT 5.5] [Gemini 3.1 Pro]

```ts
pauseContainer: (args?: Container[]) => {
  const containers = Array.isArray(args) ? args : [container];

  return Promise.all(containers.map(container =>
    this.containerRequestAction({ container, state: 'pause' })));
},
```

The pause, unpause, and restart callbacks dispatch the action as a metadata annotation patch (`containers.rancherdesktop.io/action`) via `containerRequestAction`. The patch promise only confirms that the daemon *recorded* the annotation. The actual outcome arrives asynchronously through `status.lastAction.state` (`Succeeded` / `Failed`) and `status.lastAction.error`, defined in `pkg/rdd-client/gen/models/IoRancherdesktopContainersV1alpha1ContainerStatusLastAction.ts:30-39`.

Nothing in this PR (nor the existing start/stop/delete callers it mirrors) watches `status.lastAction`, so a failed pause/unpause/restart silently disappears: the bulk `Promise.all` resolves cleanly, no banner appears, and the only signal the user gets is that `status.status` does not transition. This is a **gap** rather than a fresh regression — start/stop/delete already had it — but the repo's review context is explicit that any new annotation-action caller must either watch `status.lastAction` and surface failures, or document why no UI feedback is needed. This PR is the natural place to either close the gap for all five actions or record a deferred decision.

Fix options:

1. After dispatch, track the pending action keyed by container name. In a watcher on `containers`, when `status.lastAction.action` matches a pending request and `status.lastAction.state === 'Failed'`, commit `SET_ERROR` with `status.lastAction.error`; clear the pending entry on either `Succeeded` or `Failed`.
2. If feedback is intentionally deferred, add a comment near `containerRequestAction` (or in `Containers.vue`) that records the contract and the intentional gap, so future callers do not repeat the omission.

(important, gap)

S1. **`AbortError` suppression is broad and bypasses the reconnect path** — `pkg/rancher-desktop/store/rddConnection.ts:652-655` [Claude Opus 4.7] [Codex GPT 5.5] [Gemini 3.1 Pro]


Three independent angles converge here:

The new branch silently swallows any `DOMException` named `AbortError` and returns before `this.#loaded.reject(err)` and `this.#doneFn(err)`. `doneFn` (`pkg/rancher-desktop/store/rddConnection.ts:426-445`) is what schedules the reconnect; an aborted watch that is *not* a deliberate stop therefore stalls silently with no log line and no recovery attempt.

The repo's review context confirms that `AbortController.abort(reason)` propagates `signal.reason` verbatim through `fetch` in modern Node, so `errorManuallyStopped` survives to the existing `Object.is(err, errorManuallyStopped)` check at line 648. The same suppression is missing from the sibling `.catch()` on `this.#watcher.start()` at lines 672-680. If a future code path produces a default `AbortError` during initial watch setup (a race where `close()` fires while `doneHandler` is still awaiting `watch.watch(...)`), the catch would propagate it as a real error.

1. Add a `console.debug` line so the suppression leaves a trace, and reword the comment to acknowledge the assumption is a heuristic ("If this fires on a path we did not stop ourselves, the watcher will silently stall — no known path triggers this today").
2. Move stop-aware suppression into `ListWatch.doneHandler` where `stopped` is known, and remove the broad `AbortError` special case from `Watcher`.
