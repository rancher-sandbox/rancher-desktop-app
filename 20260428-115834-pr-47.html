S3. ListWatch leaks the body-stream of an in-flight initial list when stopped mid-await Claude Gemini¶

In cache.ts:doneHandler, the if (this.stopped) return guard runs before await this.listFn(). When Watcher.close() calls ListWatch.stop() while the inner ListWatch is awaiting its initial listFn, stopped is set to true, but after the list resolves the handler proceeds to call this.watch.watch(...), opening a fresh fetch that no caller will ever abort. The new identity guard Object.is(watcher, this.#watcher) correctly prevents stale events from corrupting state, but does not abort the leaked HTTP stream — it keeps streaming until the server closes it (typically 5–10 minutes via getRequestTimeoutMS).

This is pre-existing behaviour in the upstream-derived cache.ts; the new rewatchResources path makes it reachable by a user-initiated namespace switch. Out of diff scope but worth noting.

Design Observations ¶

Concerns ¶

  • (in-scope, future) cache.ts:doneHandler does not gate ERROR dispatch on stopped. The Watcher filters shutdown via Object.is(err, errorManuallyStopped), which works only because Watcher.close() is the sole caller passing that exact sentinel. If any future caller passes a different abort reason, the manually-stopped path silently misses it and the error propagates as a real failure, triggering an unwanted reconnect. (Fix in cache.ts — out of diff scope.) Claude

Strengths ¶

  • (in-scope) The stale-watcher identity guard Object.is(watcher, this.#watcher) in every ListWatch event handler (change, connect, error, start().catch) is the right pattern for letting the same Watcher instance survive a ListWatch swap. It centralizes the staleness decision in one form across handlers, and round 3's I2 (clearTimeout-before-check in the error handler) is now fixed in 1bc11456b. Claude Codex Gemini
  • (in-scope) Per-instance ListWatch recreation in start() (instead of restart) eliminates the previous reliance on ListWatch's fragile restart semantics — a class of subtle bugs avoided. Claude Codex
  • (in-scope) Encoding "needs rewatch on namespace change" by tracking namespacedResources: Record<string, Set<string>> keyed by Vuex module name is a clean separation: the rdd-connection module emits the trigger, but each owning module remains in charge of how to rewatch (its own rewatchResources action). Claude Gemini
  • (in-scope) Plugin<RootState> (entry/store.ts:50) is more honest than the prior per-module Plugin<ModuleState>, since plugins routinely reach into other modules' state. Claude

Testing Assessment ¶

The new logic in rddConnection.ts is not unit-tested in this PR. The most-impactful uncovered scenarios:

  1. Watcher.close() followed immediately by Watcher.start() (the rewatch path), exercising the identity guard and verifying that no stale events corrupt state — this is the critical happy path of the PR.
  2. addNamespacedResource only registers when r.namespaced=true is set on a custom-list resource, or when auto-detect picks listNamespaced<Type>; resources with custom list and no namespaced flag (e.g., systemConfigMaps) must NOT register.
  3. 429 retry path: error with statusCode=429 triggers start() after a delay (and consumes details.retryAfterSeconds from err.body once S1 is fixed).
  4. Plugin in rddConnection.ts:108-129 only dispatches rewatchResources when namespace is truthy and changed — including the documented case of transient undefined followed by reset to the initial value (the rationale the author gave for keeping the equality guard).
  5. Watch stream parser: split lines, final unterminated JSON lines, parse errors, manual abort.

Latch.settled was added without tests for resolve/reject/reset transitions; the existing latch.spec.ts:157-169 settled identifier is an unrelated local variable.

I could not run yarn lint:typescript:nofix from inside the agents' worktrees because node_modules was absent (Codex noted this).

  • Round 3 I3 *(kubernetesNamespace getter 'default' fallback)* — author chose to document the undefined-on-missing semantics in a new comment (commit 1bc11456b) rather than apply the fallback. S5 above is a wording nit on that new comment.
