## Executive Summary

This PR introduces an `App` resource to the RDD API, starts the app on UI display, and refactors resource watching from per-resource actions to a refcounted `watchResources`/`unwatchResources` API. The refactoring centralizes watch lifecycle in `setupResourceWatch`, correctly handles overlapping component lifecycles through reference counting, and cleanly separates resource definitions (plugins) from consumer lifecycle (pages). Nine important issues remain: a concurrent `fetchConfig` race between plugins that can trigger a reconnect storm (I1), a `waitForResources` timing gap where it resolves before the cache populates (I2), unrecoverable error paths in `ensureAppStarted` (I3, I4), uncaught `unwatchResources` rejections in three pages (I5), a missing merge-patch Content-Type on `containerSetState` (I6), a `waitForResources` pre-list resolution (I7), and key collisions in disconnect callbacks (I8).

## Important Issues

1. **Concurrent `fetchConfig` race between plugins** — `rddConnection.ts:54-66`, `rddConnection.ts:357-368` [Gemini P2, Codex P2] (important, regression)

```ts
while (!rddState.config.currentContext) {
  try {
    await dispatch('rdd-connection/fetchConfig', {}, { root: true });
  } catch (error) {
```

Both `rdd.ts` and `container-engine.ts` register plugins that dispatch `setupResourceWatch` at store initialization. Both run concurrently and hit the `fetchConfig` retry loop. Because `fetchConfig` is not deduplicated, the second call's `notifyDisconnected` tears down the first plugin's newly created watchers. The aborted watchers fire `doneFn`, which clears config and schedules another `setupResourceWatch` after 1 second, creating a reconnect loop.

Fix: Deduplicate `fetchConfig` so concurrent calls return the same pending promise. Clear the cached promise in a `finally` block.

2. **`waitForResources` resolves before the initial list populates the cache** — `rddConnection.ts:504-514`, `cache.ts:180-192` [Codex P2] (important, regression)

```ts
// cache.ts — CONNECT fires before listFn completes
this.callbackCache[CONNECT].forEach((elt: ErrorCallback) => elt(undefined));
if (!this.resourceVersion) {
  const promise = this.listFn();
  list = await promise;
  this.addOrUpdateItems(list.items);
}
```

`waitForResources` treats `watcher.loaded` as "first list completed," but `Watcher` resolves that latch from `onChange` on the `connect` event. In `ListWatch.doneHandler`, `CONNECT` callbacks fire before `listFn` runs and before `addOrUpdateItems` loads the cache. A slow first list lets `waitForResources` return early, so `ensureAppStarted` concludes no app exists and spams `createApp`/409.

Fix: Move the `CONNECT` callback invocation in `cache.ts` to after the initial list block completes, or resolve `Watcher.loaded` from a separate post-list signal.

3. **`ensureAppStarted` exits permanently on transient create errors** — `rdd.ts:108-117` [Claude P1] (important, regression)

```ts
} catch (err) {
  if (err instanceof Error && 'code' in err && err.code === 409) {
    // HTTP 409 Conflict means the app already exists; ...
  } else {
    console.error(err);
    commit('SET_ERROR', err as Error);
    return;
  }
}
```

Non-409 errors during `createApp` (transient 500, network timeout) cause an early `return` with no retry. The app remains permanently unstarted until the user reloads. The `waitForResources` retry loop handles connection failures well, but the create-and-patch phase has no equivalent resilience.

Fix: Wrap the create-and-patch section in a retry loop with backoff for transient errors (5xx, network), or at minimum retry before giving up.

4. **`patchApp` error silently absorbed** — `rdd.ts:126-131` [Claude P2] (important, regression)

```ts
await client.patchApp(
  { name: app.metadata.name, body: { spec: { running: true } } },
  RDDClient.setHeaderOptions('Content-Type', PatchStrategy.MergePatch),
).catch((err: Error) => {
  console.error(err);
  commit('SET_ERROR', err);
});
```

The `.catch` logs the error and commits it to state but does not rethrow. `ensureAppStarted` returns successfully to `default.vue`, which never sees an error. The app stays `running: false` permanently after a transient patch failure.

Fix: Rethrow from the `.catch` (or use try/catch) so the caller can handle the failure.

5. **`unwatchResources` rejections uncaught in three pages** — `Containers.vue:326`, `Images.vue:91`, `Volumes.vue:198` [Claude P2] (important, regression)

```ts
// Containers.vue:325-327
beforeUnmount() {
  this.unwatchResources(['containers', 'images', 'namespaces']);
},
```

`unwatchResources` awaits `state._watchersInitialized`. If the latch is rejected (e.g., `setupResourceWatch` failed during reconnect), these calls throw unhandled promise rejections. Compare with `default.vue:153` and `ContainerInfo.vue:249`, which correctly catch.

Fix: Add `.catch(err => console.error(err))` to all three call sites.

6. **`containerSetState` missing merge-patch Content-Type** — `container-engine.ts:119-127` [Gemini P1] (important, gap)

7. **`unwatchResources` may trigger spurious reconnect** — `rddConnection.ts:492-500`, `cache.ts:86-89` [Gemini P1, Codex P1] (important, regression)

```ts
if (count === 1) {
  watcherInfo.watcher.close();
}
```

When the last consumer unmounts, `close()` calls `ListWatch.stop()`, which aborts the in-flight fetch. In `ListWatch.doneHandler`, `ERROR` callbacks may fire before the `stopped` flag check, triggering the watcher's error handler and the reconnect path. Because `setupResourceWatch` on reconnect closes all watchers, this can cascade.

Fix: Guard `doneFn` to check whether the closed watcher is still the active watcher with a positive refcount, or add an `intentionallyClosed` flag in the `Watcher` class that suppresses error callbacks on explicit closure.

8. **Key collision in `disconnectCallbacks` for `namespaces`** — `rddConnection.ts:436-442` [Gemini P2] (important, regression)

```ts
await dispatch('rdd-connection/registerDisconnectCallback',
  {
    key:      r.name,
    callback: () => {
      watcher.close();
      dispatch('rdd-connection/registerDisconnectCallback', { key: r.name }, { root: true });
    },
  }, { root: true });
```

Both `rdd.ts` and `container-engine.ts` define a resource named `namespaces`. The disconnect callback key `r.name` collides: whichever plugin finishes last overwrites the other's callback. On disconnect, only the last-registered callback fires; the other watcher leaks.

Fix: Include the store module name in the key (e.g., `${moduleName}/${r.name}`) or use a unique ID per watcher instance.

9. **StatusBar reads optional spec fields not populated by `createApp`** — `StatusBar.vue:21-29`, `rdd.ts:95-105` [Codex P1] (important, regression)

```ts
kubernetesEnabled(): boolean {
  return !!this.app?.spec?.kubernetes?.enabled;
},
containerEngine(): string {
  return this.app?.spec?.containerEngine?.name || 'unknown';
}
```

`createApp` sets only `spec.namespace` and `spec.running`. The generated `AppSpec` marks `containerEngine` and `kubernetes` as optional. Until the backend populates these fields, the status bar shows "deactivated" and "unknown" — a visible regression from the previous preferences-backed values.

Fix: Populate `spec.containerEngine` and `spec.kubernetes` from preferences when creating the app, or keep preference-backed fallbacks until `app.spec` contains these fields.

## Suggestions

1. **BackendProgress shows blank indeterminate spinner** — `BackendProgress.vue:59-63` [Codex P1] (suggestion, regression)

`progressIndeterminate` now keys off `!this.running`, but the progress feed (`k8s-progress` IPC) is commented out. Startup shows a blank indeterminate bar with empty labels instead of meaningful progress.

2. **`ContainerInfo.vue` uses `onMounted` instead of `onBeforeMount`** — `ContainerInfo.vue:242` [Claude P1] (suggestion, regression)

The `watchResources` docstring says "expected to be called in a component's `onBeforeMount()` hook." All other pages use `beforeMount`. `ContainerInfo.vue` uses `onMounted` instead. Functionally correct (the watcher is likely running from the parent page), but inconsistent with the documented convention.

3. **`status` getter returns a function, bypassing Vuex caching** — `rdd.ts:49-54` [Claude P1] (suggestion, regression)

The `status` getter returns a new function on every access. Vuex getters that return functions bypass caching. Currently only called from other getters, so impact is negligible.

4. **BackendProgress test suite entirely skipped** — `BackendProgress.spec.ts:42` [Claude P1] (suggestion, gap)

The entire meaningful test suite is wrapped in `describe.skip`. The change to `progressIndeterminate` has no test coverage.

5. **Incomplete `mockModules` default** — `mockModules.ts:6-13` [Claude P1] (suggestion, gap)

The default mock for `@pkg/entry/store` provides only `mapTypedGetters`. Components using `mapTypedState`, `mapTypedMutations`, or `mapTypedActions` get `undefined`. Works for current tests but incomplete as a reusable default.

6. **Unnecessary polling loop for App resource** — `rdd.ts:98-124` [Gemini P1] (suggestion, enhancement)

The `while` loop spams `createApp` every 100ms while waiting for `getters.app` to update via the async watch. The app name is hardcoded to `'app'` in the same function. The loop could be replaced with a single `createApp` call (catching 409) and using the literal name in `patchApp`.

7. **Dead `created` getter** — `rdd.ts:55-57` [Claude P2] (suggestion, regression)

The `created` getter is defined but never consumed by any component or action.

8. **`app` getter predicate misleading** — `rdd.ts:45-47` [Claude P2] (suggestion, regression)

`find(app => !!app)` filters falsy values, but Kubernetes resource objects are always truthy. `state.apps?.[0]` is more direct.

9. **`setCurrentNamespace` replaces watch callback on reconnect** — `container-engine.ts:100-105` [Claude P2] (suggestion, regression)

`setCurrentNamespace` calls `setupResourceWatch` with a fresh callback, replacing the plugin's original `doneFn` closure. All subsequent automatic reconnects permanently use the namespace-change callback. Both callbacks are functionally equivalent today, but the coupling is fragile.

10. **`usePassthroughURL` uses module-global flag** — `passthrough.ts:19-33` [Codex P2] (suggestion, gap)

The `systemConfigMapsWatched` boolean is process-global rather than store-owned. Brittle in tests and HMR-like flows. Works correctly with the "watch once, never unwatch" pattern, but would be more robust as store state.

11. **`listFn`/watch fieldSelector divergence** — `rddConnection.ts:381-393` vs `421-423` [Claude P2] (suggestion, regression)

`listFn` evaluates selectors eagerly; the watch evaluates them lazily via functions. Both close over the same `actionContext`, so they read the same reactive getters in practice. The inconsistency is a maintainability concern — a future change could introduce a filter mismatch.

12. **`setCurrentNamespace` resets latch** — `rddConnection.ts:374` [Claude P1] (suggestion, regression)

`setupResourceWatch` replaces `_watchersInitialized` with a new unresolved latch. During a namespace change, concurrent `watchResources` or `unwatchResources` calls block until `setupResourceWatch` completes, including the config-fetch retry loop. Downgraded from Important: config is already valid during namespace changes, so the retry loop does not execute.

## Design Observations

**Concerns**

1. **(in-scope)** The watch lifecycle has no semantic distinction between intentional close and backend disconnect. `ListWatch.stop()` and a backend-initiated disconnect both fire the same error path, causing cascading reconnect logic. Moving that distinction into `ListWatch` or `Watcher` would eliminate an entire class of bugs. [Codex P1, Gemini P1, Gemini P3]

2. **(in-scope)** Two competing sources of truth for runtime settings: `preferences` and `app.spec`. Seeding `App` from preferences, or introducing a single getter that resolves the authoritative value with fallback rules, would eliminate the mixed-state problem behind I9 and simplify future consumers. [Codex P1]

3. **(in-scope)** `ensureAppStarted` mixes concerns: waiting for resources, creating the app, polling for the app in the store, and patching it to running. A more robust approach would use a Vuex store subscription or a watcher on `getters.app` instead of the 100ms polling loop. [Claude P1]

**Strengths**

1. The refcounted `watchResources`/`unwatchResources` API cleanly handles overlapping component lifecycles. When two components watch the same resource, the watcher runs as long as either is active. [All agents]

2. The `setHeaderOptions` middleware approach for overriding Content-Type avoids modifying generated code and composes well with other middleware. [Claude P1, Codex P1]

3. The `path` field as a function `(namespace: string) => string` allows namespace-scoped watch paths to use the correct namespace from connection state, rather than requiring resources to know about namespacing at definition time. [Claude P1]

4. Lazy `fieldSelector`/`labelSelector` evaluation via functions in `ListWatch` elegantly solves stale-selector bugs when Vuex state changes. [Gemini P1]

5. The `Latch` synchronization pattern for `_watchersInitialized` cleanly separates the "setup done" signal from the "data loaded" signal, allowing callers to wait at the right granularity. [Claude P1]

I2. **`setCurrentNamespace` resets `_watchersInitialized` latch, blocking concurrent `watchResources` calls** — `pkg/rancher-desktop/store/rddConnection.ts:374` (important, regression)

If the backend is slow, this could freeze component lifecycle hooks for seconds.

The `doneFn` callback is invoked whenever a watch connection terminates. This includes intentional closures triggered by `unwatchResources` (when `refCount` drops to 0 on component unmount) and `setupResourceWatch` (which proactively closes all existing watchers when reloading config or changing namespaces). ### Executive Summary

This PR introduces an `app` resource for tracking application backend progress and implements a refcounted lifecycle for resource watchers. While the refcounting mechanically allows multiple consumers to watch resources safely, the implementation introduces critical race conditions during startup because concurrent `fetchConfig` calls are not deduplicated. Furthermore, overlapping resource names across store modules overwrite disconnect callbacks, meaning some watchers will silently leak or fail to restart gracefully during connection drops.

### Findings

#### Critical Issues

C1. **Concurrent `fetchConfig` calls cause race conditions and an infinite reconnect loop** — `pkg/rancher-desktop/store/rddConnection.ts:54-66`, `pkg/rancher-desktop/store/rddConnection.ts:357-368` (critical, regression)

```typescript
      while (!rddState.config.currentContext) {
        try {
          await dispatch('rdd-connection/fetchConfig', {}, { root: true });
        } catch (error) {
```

The newly introduced `plugins` arrays in both `rdd.ts` and `container-engine.ts` dispatch `setupResourceWatch` at store initialization. Since both run concurrently and `rddState.config.currentContext` is empty at startup, they concurrently dispatch `rdd-connection/fetchConfig`.

Because `fetchConfig` is not deduplicated, multiple overlapping HTTP requests (and `ipcRenderer` invocations) are made to the backend. When the first `fetchConfig` completes, it fetches the config and resolves, allowing the first plugin to create its active watchers. Shortly after, the second concurrent `fetchConfig` resolves and calls `notifyDisconnected()`:

```typescript
      kubeConfig.loadFromString(config);
      commit('SET_CONFIG', kubeConfig);
      await dispatch('notifyDisconnected');
      commit('SET_DISCONNECT_CALLBACKS', {});
```

This clears all active connections, forcefully aborting the watchers established just milliseconds prior by the first plugin. The aborted watchers throw an `AbortError`, triggering their `doneFn` error handlers. `doneFn` logs an error, clears the `rdd-connection` config, and schedules another `setupResourceWatch` after 1000ms — initiating a permanent crash loop where each module's reconnect logic tears down the other module's watchers.

Fix: Deduplicate the `fetchConfig` action execution so that concurrent calls return the same pending promise.

```typescript
let fetchConfigPromise: Promise<RDDClient.KubeConfig> | null = null;

export const actions = {
  fetchConfig({ commit, dispatch }) {
    if (fetchConfigPromise) {
      return fetchConfigPromise;
    }
    fetchConfigPromise = (async () => {
      try {
        const config = await ipcRenderer.invoke('rdd/kube-config');
        const kubeConfig = new RDDClient.KubeConfig();

        kubeConfig.loadFromString(config);
        commit('SET_CONFIG', kubeConfig);
        await dispatch('notifyDisconnected');
        commit('SET_DISCONNECT_CALLBACKS', {});
        commit('SET_ERROR', undefined);

        return kubeConfig;
      } catch (ex) {
        commit('SET_ERROR', ex);
        throw ex;
      } finally {
        fetchConfigPromise = null;
      }
    })();
    return fetchConfigPromise;
  },
// ...
```

### Findings

#### Critical Issues

**C1. `setupResourceWatch` triggers an infinite reconnect storm on watcher replacement** — `pkg/rancher-desktop/store/rddConnection.ts:377-434`

```typescript
        for (const r of resources) {
          state._watchers[r.name]?.watcher?.close();
          const client = r.makeClient(rddState.config);
          const watcher = new Watcher(
```

When `setupResourceWatch` replaces existing watchers (e.g., during `setCurrentNamespace` or a manual reconnect), it calls `close()` on the old watcher. `close()` triggers `ListWatch.stop()`, which aborts the underlying HTTP request. This emitted `AbortError` bypasses the `this.stopped` check in `rdd-client/cache.ts` and triggers the watcher's `ERROR` callbacks, invoking the old watcher's `doneFn`.

The `doneFn` (lines 394-415) executes a devastating sequence: it clears the active `kubeConfig`, calls `notifyDisconnected` (which executes the *newly registered* disconnect callbacks and immediately kills the *new* watchers), and schedules `setupResourceWatch` to run again in 1 second. Because the new watchers are also aborted, their `doneFn` fires, perpetuating an infinite reconnect loop where the UI permanently drops its connection every second.

Fix: Add an `intentionallyClosed` flag to the `Watcher` class to suppress errors caused by explicit closure. This reliably fixes both this cascade and the known spurious reconnect issue on `unwatchResources`.

```diff
 class Watcher<
   K extends string,
   T extends RDDClient.KubernetesObject,
 > {
   #watcher:     RDDClient.ListWatch<T> | undefined;
   #type:        K;
   #namespace?:  string;
   #items:       readonly T[] = [];
   #loaded = Latch();
   #notifyDelay: ReturnType<typeof setTimeout> | undefined;
   #commit:      Commit<any>;
   #doneFn:      (error?: any) => void;
+  #intentionallyClosed = false;
 
   constructor(
...
     this.#watcher.on('error', (err) => {
+      if (this.#intentionallyClosed) {
+        return;
+      }
       // `err` is an object that calls `toString()` on `console.log`, so we
       // need to re-convert it to a plain object for better debugging.
...
   close() {
+    this.#intentionallyClosed = true;
     this.#watcher.stop();
   }
```
