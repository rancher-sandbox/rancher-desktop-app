Executive Summary ¶

This PR wires three new container actions (pause / unpause / restart) into the Containers UI by extending the existing containerRequestAction patch flow, plus two drive-by fixes: a missing Banner import in ContainerInfo.vue and AbortError suppression in the watcher's error handler. The mechanical wiring is correct and reuses the established annotation-action pattern.

The headline concern, which all three reviewers raised independently, is that none of the new action callers (nor the existing start/stop/delete callers they mirror) watches status.lastAction to surface daemon-side failures. Because the patch promise only confirms the daemon recorded the request, a failed pause/unpause/restart resolves cleanly with no banner and no log line. The repo's review context is explicit that any new annotation-action caller must either surface status.lastAction failures or document why no UI feedback is needed; this PR does neither.

Secondary concerns: the new AbortError branch is broad defense-in-depth that silently bypasses the reconnect path; Restart is disabled for stopped containers and Stop for paused containers (a UX edge worth confirming against the daemon's transition rules); pause/unpause/restart labels are hard-coded English while Delete is i18n'd via a stale images.* key.

Structure: 3 commits, each one concept; 3 files (+60/−13).

Two UX edges flow from gating both Stop and Restart on isRunning:

A paused container has no Stop action available — the user must Unpause first, then Stop. Docker accepts docker stop on a paused container directly (it kills through the paused state).

A stopped (exited / created) container has no Restart action — the user has to use Start. Restart-on-stopped is a routine Docker workflow.

If the daemon enforces these specific transitions and the UI faithfully mirrors them, that is fine. Otherwise broaden the guards: Stop on running || paused, Restart on running || paused || stopped. Confirm against the daemon's transition rules before locking the buttons out.

Design Observations ¶

Strengths ¶

  • Thin extension of an existing pattern (in-scope) Claude Codex — Reuses containerRequestAction rather than adding parallel patch code per operation. The annotation format stays centralized and the new feature surface area stays small.
  • Type tightening on RowItem (in-scope) Claude — stopContainer? / startContainer? / deleteContainer? / viewInfo? moved from optional to required, matching reality (the row mapping always provides them). Better IDE feedback.

Testing Assessment ¶

No Jest specs cover pages/Containers.vue or pages/containers/ContainerInfo.vue, consistent with how other pages in pages/ are not unit-tested today. The existing container e2e suite is under test.describe.fixme in e2e/containers.e2e.spec.ts:13, and the page object action union at e2e/pages/containers-page.ts:3 still only lists info, stop, start, and delete. This PR adds no test gap relative to convention.

Risk-ranked scenarios that would benefit from coverage if/when these pages get tests:

  1. Daemon-side action failure propagation through status.lastAction (covers I1).
  2. Pause/unpause/restart action dispatch builds the correct state payload for a single row and an array of rows.
  3. enabled predicates flip correctly across running → paused → running transitions.
  4. The AbortError suppression branch in rddConnection.ts does not stall the watcher when a real error path produces a DOMException-shaped error (covers S1).

Documentation Assessment ¶

No external documentation references the new actions, and the labels are user-facing strings rather than docstring-level concerns. The Banner import fix in ContainerInfo.vue is mechanical. Consider adding a one-line comment near containerRequestAction clarifying the daemon's async-result contract (status.lastAction), so future callers do not repeat the gap noted in I1.
