## Executive Summary

The PR renames the application to **Rancher Desktop 2**, switches the
Windows app id to `io.rancherdesktop.app2`, gives the MSI a fresh
UpgradeCode, parameterises the WiX template (`$(var.appName)`,
`$(var.appId)`), and rewires the icon flow to a real `icon.ico`. Build
plumbing is reworked so the runtime `productName` flows from
`package.json` into the electron-builder config, the macOS/Windows
signing configs, and the WiX `-d` definitions. Renderer pages and the
default layout now read `productName` from `package.json` to render the
title.

What's missing is the long tail of consumers that still hard-code
`Rancher Desktop` / `Rancher Desktop.exe` / `Rancher Desktop.app`.
`rdctl`'s app-path lookup, the e2e suite, the smoke-test installer,
`scripts/install-latest-ci.sh`, and `scripts/populate-update-server.ts`
all break the moment the rename ships. The WiX file keeps the old
`AppGUID`, so RD2 still triggers the legacy NSIS uninstall and shares
HKCU/HKLM PATH-marker keys with RD1 — the "side-by-side" goal stated in
the issue is not yet achievable. A handful of UI strings (the
`KubernetesError` version line, `app.update`) still say "Rancher
Desktop" in the same surfaces where the title now says "Rancher Desktop
2."

The build-script work is in good shape; the renderer touch-ups are
correct as far as they go; the gaps are downstream consumers, not the
files in the diff.

## Important Issues

I1. **`rdctl` cannot locate the renamed app — `Rancher Desktop.exe` and `Contents/MacOS/Rancher Desktop` hard-coded in path lookup** — `src/go/rdctl/pkg/paths/paths_windows.go:88-89,101`, `src/go/rdctl/pkg/paths/paths_darwin.go:66,68,90`, `src/go/rdctl/pkg/factoryreset/factory_reset_windows.go:43,58` [Claude Opus 4.7] [Codex GPT 5.5]

```go

return FindFirstExecutable(
    filepath.Join(appDir, "Rancher Desktop.exe"),
    filepath.Join(dataDir, "Programs", "Rancher Desktop", "Rancher Desktop.exe"),
)
```

```go
// paths_darwin.go:66-68
executablePath := []string{"Contents", "MacOS", "Rancher Desktop"}

for _, dir := range []string{appDir, "/Applications/Rancher Desktop.app"} {
```

After this PR, the installed Windows binary is `Rancher Desktop 2.exe` and the macOS bundle is `Rancher Desktop 2.app` with `Contents/MacOS/Rancher Desktop 2`. `GetRDLaunchPath` and `GetMainExecutable` (used by `rdctl start`, `rdctl shutdown`, autostart on every platform) will not find the app. The same pattern shows up in `factory_reset_windows.go:43,58` (the `tasklist` filter looking for the running process by image name) and in `paths_windows.go:101` (shutdown path).

The strings predate the PR, but the rename turns them from working into broken — `rdctl` is the primary CLI for the app and is shipped inside the same MSI/zip as the app itself.

Fix: introduce a single product-name constant (or `ldflags -X` build value) read by `rdctl` so the Go side stays in lockstep with `package.json`. Keep RD1 fallback paths only if migration is wanted.

I2. **WiX `AppGUID` unchanged from RD1 — RD2 install removes RD1 and shares PATH-marker registry keys** — `build/wix/main.wxs:35,80-110,113-160` [Codex GPT 5.5] [Claude Opus 4.7]

```xml
<WixVariable Id="AppGUID" Value="358d85cc-bb94-539e-a3cd-9231b877c7a4" />
```

```xml
<Property Id="NSISUNINSTALLCOMMAND">
  <RegistrySearch
    Root="HKCU"
    Key="Software\Microsoft\Windows\CurrentVersion\Uninstall\!(wix.AppGUID)"
    ...
```

The `UpgradeCode` was rotated to `{37829D57-…}`, which makes the MSI a distinct product. The `AppGUID` was not. Three consequences follow:

1. The `UninstallNSIS` action (lines 80-110) runs on every fresh RD2 install and removes the legacy NSIS-era RD1 if it was installed under the same `AppGUID`. RD2 silently uninstalls RD1.
2. The `PathUser`/`PathSystem` components (lines 113-160) write the `EnvironmentVariablesSet` marker under `HKCU\SOFTWARE\!(wix.AppGUID)` and `HKLM\SOFTWARE\!(wix.AppGUID)`. RD1 MSI and RD2 MSI both write to the same key. Whichever uninstalls first removes the marker; the other product is left believing it has not yet set PATH.
3. The `FirewallException` rules (lines 183-198) hard-code `Rancher Desktop Networking …` as their display name. Two installed products produce two firewall rules with identical visible names.

Fix: give RD2 a fresh `AppGUID` (rotate the GUID and update the references at lines 35, 85, 117, 142). Either remove the NSIS-uninstall block from RD2 or guard it explicitly on a "this is RD1" condition. Parameterise the firewall display names via `$(var.appName)`.

I3. **macOS signed artifact names diverge from `populate-update-server.ts` expectations** — `scripts/lib/sign-macos.ts:146-148`, `scripts/populate-update-server.ts:128-130` [Codex GPT 5.5]

## Suggestions

S1. **`outDir` parameter is mandatory, but its `||` fallback is unreachable** — `scripts/lib/installer-win32.tsx:75` [Claude Opus 4.7]

```ts
const outFile = path.join(outDir || path.join(process.cwd(), 'dist'), installerName);
```

Pre-PR the third arg was an optional `outFile = ''`. After the PR it is `outDir: string` (required) and all callers (`scripts/wix.ts:28`, `sign-win32.ts:115,196`, `scripts/package.ts:210`) pass non-empty strings. The `||` branch is dead code.

Fix:

```diff
-const outFile = path.join(outDir || path.join(process.cwd(), 'dist'), installerName);
+const outFile = path.join(outDir, installerName);
```

S2. **`${ '' }` spell-check workaround can be replaced by splitting the candle args** — `scripts/lib/installer-win32.tsx:99-103` [Claude Opus 4.7]

```ts
`-d${ '' }appDir=${ appDir }`,
`-d${ '' }appName=${ productName }`,
`-d${ '' }appId=${ electronBuilderConfig.appId }`,
`-d${ '' }iconPath=${ iconPath }`, // spellcheck-ignore-line
`-d${ '' }licenseFile=${ path.join(appDir, 'build', 'license.rtf') }`,
```

`candle.exe` accepts `-d KEY=VALUE` as two arguments. Splitting drops the `${ '' }` hack and the leftover `// spellcheck-ignore-line` comment, and avoids the asymmetry where four of five lines have the empty-template hack but one line keeps the comment too. The author has explained the hack in inline review (acknowledged limitation), so this is offered as a cleaner equivalent rather than a refutation.

Fix:

```diff
-`-d${ '' }appDir=${ appDir }`,
-`-d${ '' }appName=${ productName }`,
-`-d${ '' }appId=${ electronBuilderConfig.appId }`,
-`-d${ '' }iconPath=${ iconPath }`, // spellcheck-ignore-line
-`-d${ '' }licenseFile=${ path.join(appDir, 'build', 'license.rtf') }`,
+'-d', `appDir=${ appDir }`,
+'-d', `appName=${ productName }`,
+'-d', `appId=${ electronBuilderConfig.appId }`,
+'-d', `iconPath=${ iconPath }`,
+'-d', `licenseFile=${ path.join(appDir, 'build', 'license.rtf') }`,
```

S3. **`installer-win32-gen.tsx` uses the `@/scripts/...` alias for a sibling import** — `scripts/lib/installer-win32-gen.tsx:8` [Claude Opus 4.7]

```ts
import buildUtils from '@/scripts/lib/build-utils';
```

The other file in the same directory (`installer-win32.tsx:17`) imports the same module as `import buildUtils from './build-utils'`. The relative form is consistent with the neighbour and shorter.

Fix:

```diff

+import buildUtils from './build-utils';
```

S4. **`electron-builder.yml` keeps a `productName` value the build script always overrides** — `packaging/electron-builder.yml:3` [Claude Opus 4.7]

```yaml
productName: Rancher Desktop
```

`scripts/package.ts:146` runs `_.set(config, 'productName', buildUtils.packageMeta.productName)` unconditionally before `electron-builder.build()`, so the YAML value is dead. Future maintainers editing this file expecting the change to take effect will be silently ignored.

Fix: delete the line (let `_.set` populate it) or replace it with a comment pointing at `package.json` and `package.ts`.

S5. **`build/signing-config-win.yaml` mirrors a value the build script always rewrites** — `build/signing-config-win.yaml:7` [Claude Opus 4.7]

```yaml
.:
- Rancher Desktop 2.exe
```

`scripts/package.ts:279-281` rewrites any entry matching `^Rancher Desktop.*\.exe$` to `${productName}.exe` before electron-builder packs it. The literal `Rancher Desktop 2.exe` here is redundant — `Rancher Desktop.exe` would survive the regex equally well, and using the unsuffixed form aligns with `signing-config-mac.yaml` which still uses the unsuffixed helper names. Pick one source-of-truth convention and apply it to both files.

S6. **Linux AppStream `<id>` and `<binary>` are unchanged — RD1 and RD2 collide on distros that read `appdata.xml`** — `packaging/linux/rancher-desktop.appdata.xml:3,14` [Claude Opus 4.7]

```xml
<id>rancher-desktop</id>
…
<binary>rancher-desktop</binary>
```

`createLinuxResources` in `scripts/package.ts:217-233` rewrites `<release>` and `<name>` but leaves `<id>` and `<binary>` alone. AppStream IDs are required to be globally unique; a flatpak/snap/.deb that bundles RD2 with this XML cannot coexist with RD1's metadata. The Linux distribution path runs through OBS today and may not exercise this, so the impact is theoretical — flag for the eventual full rebrand.

S7. **MSI installer filename strips the trailing version digit, producing the same name as RD1's MSI** — `scripts/lib/installer-win32.tsx:73-74` [Gemini 3.1 Pro] [Claude Opus 4.7]

```ts
// Strip any versions, to avoid `Rancher Desktop 2 Setup 1.2.3.msi`.
const unversionedName = productName.replace(/\s*[\d.]+$/, '');
const installerName = `${ unversionedName.replace(/\s+/g, '.') }.Setup.${ appVersion }.msi`;
```

The regex strips ` 2` from `Rancher Desktop 2`, leaving the final filename as `Rancher.Desktop.Setup.1.99.0.msi` — bit-for-bit identical to RD1's MSI name. The code comment shows the intent ("avoid `Rancher Desktop 2 Setup 1.2.3.msi`") so this is deliberate, but a user with both downloads cannot tell them apart, and the GitHub Actions artifact label is `Rancher Desktop Setup.msi` (no `2`) for the same reason. Consider keeping the productName as-is (`Rancher.Desktop.2.Setup.1.99.0.msi`) and adjusting the `Rancher.Desktop*.msi` glob in `populate-update-server.ts` and CI accordingly.

S8. **Bulk hard-coded `Rancher Desktop` strings remain in `en-us.yaml` and `background.ts`** — `pkg/rancher-desktop/assets/translations/en-us.yaml` (lines 178, 329, 357-358, 477, 481, 484, 489, 495-497, 504-505, 510-512, 4813, 4827-4828, 4837), `background.ts:308-320` [Gemini 3.1 Pro] [Claude Opus 4.7]

The PR parameterised `app.name` and `general.title` but ~20 other user-visible strings still say "Rancher Desktop" verbatim. Most are sentences in mid-flow ("Rancher Desktop will be temporarily unavailable…", "Quit Rancher Desktop") rather than identifiers, and substituting `{productName}` in each one is mechanical. A follow-up sweep through the file plus `background.ts` (the unable-to-start error messages) will close the loop. Out of scope for "start being," but the strings are co-located with the lines this PR already touched, so it's the right moment.

## Design Observations

### Concerns

- **Multiple sources of truth for the product name** *(in-scope)* [Claude Opus 4.7]. The rename touches `package.json` (productName), `electron-builder.yml` (overridden in code), `build/signing-config-win.yaml` (regex-rewritten), `build/signing-config-mac.yaml` (regex-rewritten), `build/wix/main.wxs` (parametrised via `$(var.appName)`), and `installer-win32-gen.tsx` (computed key in JSX). Three different mechanisms (override, rewrite, parametrise) for the same conceptual value. The next renamer (RD3?) needs to remember which files self-update and which do not. A single "branding bundle" emitted at build time and consumed by every downstream file would shrink this surface. Closely related to I1 (`rdctl` Go side has yet another copy).

- **Source-tree mutation during packaging** *(in-scope)* [Gemini 3.1 Pro]. `scripts/package.ts::createWindowsResources` writes the generated icon to `resources/icons/icon.ico` directly inside the working tree. The `.gitignore` addition keeps it out of `git status`, but writing under `resources/` is an anti-pattern for a packaging script. Writing the icon to `dist/` (or `workDir`) and referencing it via `extraResources` in `electron-builder.yml` would keep the build idempotent and the source tree pristine.

### Strengths

- **Mac `.app` bundle lookup is now rebrand-proof** *(in-scope)* [Claude Opus 4.7]. `scripts/lib/sign-macos.ts:48-53` switched from a literal `Rancher Desktop.app` to a directory listing of `*.app`. The same pattern (glob with sanity check) would fix I4's smoke-test issue.

- **WiX is correctly parameterised** *(in-scope)* [Claude Opus 4.7] [Gemini 3.1 Pro]. `$(var.appName)` and `$(var.appId)` replacing literal strings in `main.wxs` and `installer-win32-gen.tsx` is exactly the right pattern for a parametric installer. The remaining hard-codes are the AppGUID and firewall display names (I2).

- **`createLinuxResources` migrated from regex `replaceInFile` to a real DOM rewrite** *(in-scope)* [Claude Opus 4.7]. The new code correctly handles the `SOURCE_DATE_EPOCH=0` edge case at `scripts/package.ts:220-222`.

- **Side-by-side install primitives are in place** *(in-scope)* [Gemini 3.1 Pro]. Rotating the `appId` to `io.rancherdesktop.app2` and the WiX `UpgradeCode` to a fresh GUID gives RD2 its own MSI identity. Once I2 (AppGUID) is resolved, the foundation for parallel install is sound.

## Testing Assessment

No new tests in this PR. Risk-ranked gaps:

1. **Side-by-side install / uninstall on Windows** — the headline feature. Manual verification needed: install RD1 NSIS, install RD2 MSI, observe whether RD1 disappears (currently expected to: see I2). Same for MSI RD1 + MSI RD2. Inverse-uninstall direction matters too because of the shared HKCU/HKLM `\AppGUID` PATH-marker key.
2. **Side-by-side install on macOS** — drag both `.app` bundles to `/Applications`, verify both launch and produce separate user-data directories. The macOS-side concern is rdctl, not the bundle itself.
3. **`rdctl` against an installed RD2** (I1) — every command that resolves the app path (`rdctl start`, `rdctl shutdown`, autostart enable/disable) needs coverage. Today none of these will find the renamed binary.
4. **e2e suite** (I4) — `yarn test:e2e` is expected to fail at the first title assertion. The PR should run the suite locally or in CI to surface the full breakage list.
5. **MSI signing path** — `signing-config-win.yaml` is now regex-rewritten at build time. A manual run that compares the produced `dist/signing-config-win.yaml` against expectations and runs `yarn sign` would confirm the rewrite works against the renamed `Rancher Desktop 2.exe`.
6. **Mac helper-app signing** — `createMacResources` rewrites `entitlements.overrides[].paths` from `^Rancher Desktop` → `${productName}`. A real signing run is needed to confirm the renamed paths match the helper bundles electron-builder produces under the new productName (the bundles are normally named after `productName`, but child helpers like `Rancher Desktop Helper.app` follow Electron-internal conventions that may not match the regex).

## Review Process Notes

### Repo context updates

- **ADD: `productName` is set in `package.json`, not `electron-builder.yml`.** The packaging script (`scripts/package.ts`) overrides the YAML value at build time with `_.set(config, 'productName', buildUtils.packageMeta.productName)` before electron-builder runs. When reviewing branding or rename changes, treat `package.json:productName` as the source of truth and trace consumers from there. The YAML value is dead code.

- **ADD: Side-by-side install identity is split across three GUIDs in WiX.** The MSI's `<Product UpgradeCode>` controls major-upgrade behaviour (different UpgradeCode = different product). The `<WixVariable Id="AppGUID">` controls (a) NSIS-uninstall registry search and (b) HKCU/HKLM `SOFTWARE\<AppGUID>\EnvironmentVariablesSet` PATH-marker keys. Each component's `Guid` is its own value. ### Executive Summary

While the architectural configuration (App ID and UpgradeCode updates) correctly isolates the new version, there is a critical logic error in the Windows installer generation that inadvertently strips the "2" from the final MSI filename, and a regression in the end-to-end tests caused by the dynamically updated UI title.

### Findings

#### Critical Issues

C1. **MSI installer filename strips product major version** — `scripts/lib/installer-win32.tsx:69-70` (critical, regression)

```typescript
  const { productName } = electronBuilderConfig;
  // Strip any versions, to avoid `Rancher Desktop 2 Setup 1.2.3.msi`.
  const unversionedName = productName.replace(/\s*[\d.]+$/, '');
  const installerName = `${ unversionedName.replace(/\s+/g, '.') }.Setup.${ appVersion }.msi`;
```

The regex `/\s*[\d.]+$/` is intended to strip trailing version numbers from the product name to prevent duplicate versioning in the installer filename. However, because the new `productName` is exactly `"Rancher Desktop 2"`, the regex matches the trailing ` 2` and inadvertently removes it. This results in the MSI filename being generated as `Rancher.Desktop.Setup.<version>.msi` instead of the expected `Rancher.Desktop.2.Setup.<version>.msi`, breaking the naming consistency of the new branding.

Fix: Refine the regex to only match true version string patterns (e.g., requiring at least one dot), or omit the version-stripping logic entirely since `productName` is explicitly set in `package.json` without the app version.

```diff
-  const unversionedName = productName.replace(/\s*[\d.]+$/, '');
+  const unversionedName = productName.replace(/\s*\d+\.\d+.*$/, '');
```
