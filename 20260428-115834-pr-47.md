S1. **429 retry never reads server-suggested `retryAfterSeconds` because `err.body` is undefined** — `pkg/rancher-desktop/store/rddConnection.ts:652-661`, `pkg/rdd-client/watch.ts:131-138` [Claude Opus 4.7]

```ts

  let delay = 0.1;
  try {
    const body = JSON.parse(err.body);
    delay = body?.details?.retryAfterSeconds ?? delay;
  } catch { /* ignore */ }
  this.#restartTimeout = setTimeout(() => this.start(), delay * 1_000);
  return;
}
```

Commit `43c3f191d` correctly fixes the predicate from `err.code === 429`
(matching `ApiException`) to `err.statusCode === 429` (matching the watch
endpoint error). That's the right fix — pre-PR the branch never fired for
the watch path, which is the only path the comment describes
("storage is (re)initializing"). However, the body the watch path throws
is constructed at `pkg/rdd-client/watch.ts:131-138` with only
`statusCode`; there is no `body` field:

```ts
const error = new Error(statusText) as Error & {
  statusCode: number | undefined;
};
error.statusCode = response.status;
throw error;
```

So `err.body` is always `undefined`, `JSON.parse(undefined)` throws,
the catch swallows it, and `delay` stays at the hardcoded 100ms regardless
of any backoff hint the server provided. Practical impact is low — 100ms
is a reasonable retry interval — but the body-parsing block is dead code
and the comment implies the retry honors backend guidance. Either populate
`err.body` from `response.text()` and update the augmentation, or delete
the dead JSON-parse block.

```diff

         const statusText = response.statusText || 'Internal Server Error';
+        const body = await response.text().catch(() => '');
         const error = new Error(statusText) as Error & {
           statusCode: number | undefined;
+          body:       string;
         };
         error.statusCode = response.status;
+        error.body = body;
         throw error;
       }
```

(suggestion, regression — Claude raised at Important; consolidator
demotes since the practical retry behaviour is benign and the body
parser is purely defensive.)

S2. **`onChange` bound to `'connect'` commits an empty list before the initial list resolves** — `pkg/rancher-desktop/store/rddConnection.ts:634-639,686-701`, `pkg/rdd-client/cache.ts:180-185` [Claude Opus 4.7]

```ts
watcher.on('connect', () => {
  // Only trigger a change if this is the current watcher.
  if (Object.is(watcher, this.#watcher)) {
    this.onChange();
  }
});
```

`ListWatch.doneHandler` (cache.ts) emits `CONNECT` *before* awaiting
`listFn()`. When `rewatchResources` runs `close(); start();` on a
namespace change, the new watcher's CONNECT handler fires before its
initial list resolves. `Watcher.onChange()` schedules a `setTimeout(0)`
that reads `this.#watcher.list(this.#namespace)` — empty at that point —
and commits `SET_<TYPE>([])`. The next `change` event then commits the
populated data.

The comment at lines 551-552 says "We may temporarily have stale data
before the new watch applies; that is acceptable, and reduces flickering"
— but the actual transient is *empty*, not stale. On a slow list this
causes a visible blank-then-repopulate flash on every namespace change.

Fix options: drop the `connect` → `onChange` binding (CONNECT only fires
when there is nothing to commit), or track a "had-data" flag and only
commit on the first non-empty `change`.

(suggestion, regression — surfaced more often by the new rewatch path.)

S3. **`ListWatch` leaks the body-stream of an in-flight initial list when stopped mid-await** — `pkg/rdd-client/cache.ts:165-214`, `pkg/rancher-desktop/store/rddConnection.ts:537-555` [Claude Opus 4.7, Gemini 3.1 Pro]

In `cache.ts:doneHandler`, the `if (this.stopped) return` guard runs
*before* `await this.listFn()`. When `Watcher.close()` calls
`ListWatch.stop()` while the inner `ListWatch` is awaiting its initial
`listFn`, `stopped` is set to `true`, but after the list resolves the
handler proceeds to call `this.watch.watch(...)`, opening a fresh fetch
that no caller will ever abort. The new identity guard
`Object.is(watcher, this.#watcher)` correctly prevents stale events from
corrupting state, but does not abort the leaked HTTP stream — it keeps
streaming until the server closes it (typically 5–10 minutes via
`getRequestTimeoutMS`).

This is pre-existing behaviour in the upstream-derived `cache.ts`; the
new `rewatchResources` path makes it reachable by a user-initiated
namespace switch. Out of diff scope but worth noting.

## Design Observations

### Concerns

- *(in-scope, future)* `cache.ts:doneHandler` does not gate ERROR
  dispatch on `stopped`. The `Watcher` filters shutdown via
  `Object.is(err, errorManuallyStopped)`, which works only because
  `Watcher.close()` is the sole caller passing that exact sentinel. If
  any future caller passes a different abort reason, the
  manually-stopped path silently misses it and the error propagates as a
  real failure, triggering an unwanted reconnect. (Fix in cache.ts —
  out of diff scope.) [Claude Opus 4.7]

### Strengths

- *(in-scope)* The stale-watcher identity guard
  `Object.is(watcher, this.#watcher)` in every `ListWatch` event
  handler (`change`, `connect`, `error`, `start().catch`) is the right
  pattern for letting the same `Watcher` instance survive a `ListWatch`
  swap. It centralizes the staleness decision in one form across
  handlers, and round 3's I2 (clearTimeout-before-check in the `error`
  handler) is now fixed in `1bc11456b`. [Claude Opus 4.7, Codex GPT 5.5,
  Gemini 3.1 Pro]
- *(in-scope)* Per-instance `ListWatch` recreation in `start()`
  (instead of restart) eliminates the previous reliance on ListWatch's
  fragile restart semantics — a class of subtle bugs avoided.
  [Claude Opus 4.7, Codex GPT 5.5]
- *(in-scope)* Encoding "needs rewatch on namespace change" by tracking
  `namespacedResources: Record<string, Set<string>>` keyed by Vuex
  module name is a clean separation: the rdd-connection module emits
  the trigger, but each owning module remains in charge of how to
  rewatch (its own `rewatchResources` action). [Claude Opus 4.7,
  Gemini 3.1 Pro]
- *(in-scope)* `Plugin<RootState>` (entry/store.ts:50) is more honest
  than the prior per-module `Plugin<ModuleState>`, since plugins
  routinely reach into other modules' state. [Claude Opus 4.7]

## Testing Assessment

The new logic in `rddConnection.ts` is not unit-tested in this PR. The
most-impactful uncovered scenarios:

1. `Watcher.close()` followed immediately by `Watcher.start()` (the
   rewatch path), exercising the identity guard and verifying that no
   stale events corrupt state — this is the critical happy path of the
   PR.
2. `addNamespacedResource` only registers when `r.namespaced=true` is
   set on a custom-list resource, or when auto-detect picks
   `listNamespaced<Type>`; resources with custom `list` and no
   `namespaced` flag (e.g., `systemConfigMaps`) must NOT register.

   a delay (and consumes `details.retryAfterSeconds` from `err.body`
   once S1 is fixed).

   `rewatchResources` when namespace is truthy and changed — including
   the documented case of transient `undefined` followed by reset to
   the initial value (the rationale the author gave for keeping the
   equality guard).
5. Watch stream parser: split lines, final unterminated JSON lines,
   parse errors, manual abort.

`Latch.settled` was added without tests for resolve/reject/reset
transitions; the existing `latch.spec.ts:157-169` `settled` identifier
is an unrelated local variable.

## Executive Summary

This PR replaces the hard-coded `'rancher-desktop'` Kubernetes namespace with a reactive read from the App CR's `spec.namespace`, plus a reconnect/rewatch pipeline that re-issues watches when the namespace changes. The store-side restructuring is sound: per-resource reconnect timeouts, a stale-watcher identity guard via `Object.is(watcher, this.#watcher)`, and `addNamespacedResource` tracking via `Set<string>` are well-fitting. One latent inconsistency persists in the 429 retry path, and several stale comments and minor design observations remain.

### Important Issues

I1. **429 retry never reads server-suggested `retryAfterSeconds` because `err.body` is undefined** — `pkg/rancher-desktop/store/rddConnection.ts:652-661`, `pkg/rdd-client/watch.ts:131-138`

```ts
} else if (err.statusCode === 429) {
  // We can get this if we request too early (when the backend restarts),
  // with a message of "storage is (re)initializing".  Just retry.
  let delay = 0.1;
  try {
    const body = JSON.parse(err.body);
    delay = body?.details?.retryAfterSeconds ?? delay;
  } catch { /* ignore */ }
  this.#restartTimeout = setTimeout(() => this.start(), delay * 1_000);
  return;
}
```

Commit `43c3f191d` correctly fixes the field-name bug (`err.code` → `err.statusCode`), so the 429 branch now actually fires. However, `pkg/rdd-client/watch.ts:131-138` constructs the error with only `statusCode` set; there is no `body` field:

```ts
const error = new Error(statusText) as Error & {
  statusCode: number | undefined;
};
error.statusCode = response.status;
throw error;
```

`err.body` is therefore always `undefined`, `JSON.parse(undefined)` throws, the catch swallows it, and `delay` stays at the hardcoded 100ms regardless of what the server told us via `Retry-After` or `details.retryAfterSeconds`. The body-parsing block is dead code as currently wired. Before the field-name fix the branch never fired so this was inert; now that 429 is reachable, the broken `Retry-After` handling is observable behavior.

Severity: IMPORTANT, gap. Practical impact is low (the watcher will retry indefinitely at 100ms intervals and self-heal once the backend storage is initialized), but the resulting tight retry loop can amplify load on a backend that explicitly asked clients to back off.

Fix: in `pkg/rdd-client/watch.ts:131-138`, read the response body before throwing so `err.body` exists for the 429 path. The error type already needs to be augmented:

```diff
       } else {
         const statusText = response.statusText || 'Internal Server Error';
+        const body = await response.text().catch(() => '');
         const error = new Error(statusText) as Error & {
           statusCode: number | undefined;
+          body:       string;
         };
         error.statusCode = response.status;
+        error.body = body;
         throw error;
       }
```

(Reading the response text fully is safe here because we already chose not to stream this branch.) Alternatively, prefer the standard `Retry-After` HTTP response header and pass it through on the error.

S2. **`setupResourceWatch called more than once` guard locks out recovery if initial setup throws** — `pkg/rancher-desktop/store/rddConnection.ts:371-374, 463-466`

```ts
      if (state._watchersInitialized.settled) {
        // This should never happen, but guard against it just in case.
        throw new Error('setupResourceWatch called more than once');
      }
      ...
      } catch (error) {
        state._watchersInitialized.reject(error);
        throw error;
      }
```

`Latch.settled` becomes `true` on both `resolve` and `reject` (per the new `latch.ts:101-103, 109-111`). If the inner loop throws — e.g., because of the `Client X does not have a list function for resource type ...` error at line 407 — the latch is rejected, `settled` becomes `true`, and any subsequent retry attempt by anything (current code or future caller) hits the "called more than once" branch even though the resources were never set up. Recovery requires recreating the store.

In current code there is exactly one caller (the plugin) that does not retry, so this is latent. But the comment says "should never happen" while a programming-error path makes it permanent.
